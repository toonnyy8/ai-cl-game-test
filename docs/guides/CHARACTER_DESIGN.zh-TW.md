# 角色設計與開發手冊（以利傑·巴羅為範本）

這份手冊把 SOUL DUEL 第六位角色「利傑·巴羅」（Lille Barro，2026-10-06 → 10-08）的設計與開發經驗，整理成下一個角色可以直接照著走的做法。使用者說這是目前最滿意的角色設計，但過程中也改了很多次：3 天裡做了 56 個決定，其中 41 個是試玩之後才改的。這份手冊的目的有兩個：保留做對的方法，並把「早問一句就不用重來」的地方標出來。

- 標 **⚠ 先確認** 的項目，請在動手前先問使用者，不要先做再改。每一項都附上利傑這次因為沒先問而付出的代價。
- 細節與出處：[`docs/duel/DUEL_LILLE.md`](../duel/DUEL_LILLE.md)（設計與每個決定）、[`docs/research/lille-retrospective/digest.md`](../research/lille-retrospective/digest.md)（56 個決定的時間線、重工熱點、數字），DEVLOG §84–§135。
- 對應的 Claude skill：`skills/duel-character/`（從零設計新角色）、`skills/duel-character-rework/`（修改現有角色）。通用流程仍是 [PLAYBOOK.zh-TW.md](PLAYBOOK.zh-TW.md) 與 `game-dev-workflow`。

重工幾乎都集中在兩類：**手感數值**（距離、時間長度、慢動作倍率）和**輪廓造型**（翼、腿、兩種模式看起來是否不同）。規則本身的意圖一旦確定，就很少再改。所以**要先問的是「意圖」和「單位」，數值則交給試玩去調**。

## 1. 開工前必須先確認的設計意圖（⚠ 清單）

照順序問。每一題都用 AskUserQuestion 給 2–4 個選項，推薦的放第一個；沒選的選項也要寫進設計文件。

### 1.1 概念階段

| ⚠ | 要問的問題 | 利傑的教訓（代價） |
|---|---|---|
| ⚠ 角色定位對上全陣容 | 「他被貼到 2 m 時要做什麼？」，而不只是問「他是遠程還是近戰」 | 決定 1 選了「純遠距狙擊、沒有逃生手段」，結果面對全員衝臉的 CPU，83–93% 的時間都在 6 m 內，加傷害、減受傷都救不了，最後兩度重建規則（決定 17、21–23，約 4 個決定）。**動工前先用 10 個種子量「各距離停留時間」** |
| ⚠ 每個型態怎麼進得去 | 「練習模式裡，試玩的人要怎麼進到這個型態？」 | 決定 8 的「被斬首後復活」在練習模式根本進不去，梟頭無法試玩，改成魂魄 ≤ 4 就能復活（決定 16） |
| ⚠ 覺醒是「同系統加強」還是「新系統」 | 「第二段覺醒玩起來像第一段的強化版，還是一套新的招式？」 | 梟頭原本是獨立的一套招式，有了 EN／KIN 兩種模式後讀起來像另一個角色，整套重做成 Jilliel 的系統（決定 36，新增 425 項測試） |
| ⚠ 能否沿用現有系統的形狀 | 「這個機制可以當成某某角色那套的變體嗎？」 | 這次做對了：無實體 = 山本西 + 一個旗標、架式 = 一護的月待、復活 = 劍八卍解的流程。做得快、不影響其他角色、平衡也有前例 |

### 1.2 機制設計階段

| ⚠ | 要問的問題 | 利傑的教訓（代價） |
|---|---|---|
| ⚠ 位移招式的落點與運動模型 | 「衝刺後要停在離對手多遠？固定時間還是固定速度？用幾個 Step 的長度表示？衝刺後的那一下 J 會不會再往前移？」 | 天震的距離前後改了 8 次。決定 52 縮短距離卻沒效果，因為決定 25 加的「連段追擊」還會把 J1 從約 11 m 外拉過去。直到決定 53 改成固定 30 m/s、拿掉追擊才收斂。**約 13 個決定、11 次閘門** |
| ⚠ 列出招式上所有「隱藏位移」 | 追擊（Breaker 規則）、出招前衝、連段追擊各自會怎麼移動？ | K → L 的 bug：連段追擊在天震前搖時把他往前拉，7 m 的後撤實際只退了 0.88 m（決定 43） |
| ⚠ 節奏怎麼控制、取消能否被濫用 | 「什麼東西阻止他一直按？攻擊取消能不能免費跳過前搖？」對每一條取消路線都用對抗的角度檢查一次 | 空揮就能買到 2 f 取消，是使用者自己發現的漏洞（決定 35） |
| ⚠ 延遲傷害的命中意圖 | 「軌跡什麼時候該穩定打中？對手又該怎麼應對？」 | 先做成不造成傷害的軌跡，又加上 1 點傷害的射擊（決定 39），結果反而讓 CPU 找到幾乎無法反應的開局，最後拿掉，改成吸附加慢動作（決定 41），**3 個決定、1 筆例外作廢** |
| ⚠ 手感效果的用途與觸發單位 | 「慢動作是提示，還是給人反應的時間？每條線各觸發一次，還是靠近時觸發一次？重疊的線算一次嗎？」 | 跨越慢動作改了 6 次，CPU 搜尋因此重新凍結 2 次、重開 1 次。**觸發規則先講定，倍率和秒數做成即時可調的旋鈕交給試玩** |
| ⚠ 會影響閘門時鐘的效果 | 慢動作、過場會不會讓比賽秒數變長？ | 慢動作改變了步進的量化，勝場跟著動；過場變長，中位數也跟著漲，最後才定下「閘門時長不計過場」（DEVLOG §134） |

### 1.3 建模與造型階段

| ⚠ | 要問的問題 | 利傑的教訓（代價） |
|---|---|---|
| ⚠ 哪個部位負責打、手臂看不看得到 | 「哪個部位造成傷害？手臂要畫出來嗎？」配一張出招命中幀的截圖（從背後的預設鏡頭拍） | 第一版把可見的翼掛在手臂骨架上，看起來像「手臂變成一對翅膀」，重做成八片獨立的翼（決定 19） |
| ⚠ 大型半透明或前景部件會不會擋住戰鬥 | 「從他背後看，還看得到對手嗎？」 | 翼不透明會擋視線（決定 27）；KIN 的翼直接往後伸，在背後鏡頭裡太顯眼；梟頭匯聚時翼面朝鏡頭，把爪子蓋住了 |
| ⚠ 腿與身體的拓撲 | 先給側面截圖問：「結構是這樣嗎？」 | 梟頭的腿：高蹺 → 分叉 → ㄇ 字（決定 20、26） |
| ⚠ 兩種模式的輪廓要不要一眼就分得出來 | 「遠程和近戰模式，從遠處看要長得不一樣嗎？」 | 決定 38：「目前看不出翼張開站直／翼往後收前傾」 |
| ⚠ 動作的標準 | 「每一招都要有自己的輪廓和全身動作，還是同一個揮擊重複用？」最好指定一個參考（例如「像 Jilliel 的 J/K」） | Jilliel 的 J/K（決定 50）、梟頭的 J/K 和 SP（決定 56）都是因為「動作不明顯」才重做。標準在第一個型態就定好，所有型態照同一個標準做 |

### 1.4 演出階段

| ⚠ | 要問的問題 | 利傑的教訓 |
|---|---|---|
| ⚠ 過場開始時演員在哪裡 | 「毀魂技過場開始時，兩人要不要先擺到固定距離？」 | 分鏡照 6 m 設計，但毀魂技在任何距離都會命中，桌面版對手因此掉出畫面。改用 `CINE-PLACE` 把兩人放到 6 m，結束再放回原位 |
| ⚠ 橫式與直式都要看 | 每一個鏡頭都在 1280×720 和手機直式各拍一張 | 手機很好，桌面版的下方黑邊（9%）把對手蓋住了 |
| ⚠ 分鏡用文字定稿 | 先交一張逐鏡表（幀、角度、距離、高度、焦距、畫面內容），再做 | 使用者看了逐鏡拆解之後，才精準指出「第三幕太快、第一幕太短」 |

### 1.5 用詞要換成數字確認

口語裡相對的量詞很容易誤讀，**動手前先把自己的理解換成數字，請使用者確認**：

- 「放慢 1 倍」：原本讀成 0.5 倍，使用者的意思是 0.1 倍（決定 43）。
- 「多一組手臂」：是相對於 KIN（KIN 不畫手臂）而言，所以只要一對，結果多畫了一組（決定 31：「多了一組手臂喔www」）。
- 「閃步」：使用者指的只有 Hoho，不是所有閃步（決定 37）。

## 2. 流程：每個階段做什麼

1. **概念討論**（還不寫程式）：查原作設定並分級標註（[manga]／[anime-only]／[ours]），從參考圖整理出模型設定表，問完 §1.1 的 ⚠。討論的同時可以先派 agent 準備環境、做研究。
2. **完整寫出設計文件，再做一次對抗式審查**：利傑這次審出 22 個問題，其中一個是會卡住開發的問題：放開瞄準鍵後準心還會繼續追蹤，12–20 m 用 Step 根本閃不掉，「鎖定規則」就是因此加上的。
3. **第一批先做「能玩的版本」**：規則、CPU 反射、功能性的美術（判定範圍正確即可），用 10 個種子量一次各距離停留時間和勝場。
4. **發試玩**：把整個遊戲發成私人 Artifact，每一輪更新同一個網址。使用者的手感就是平衡的裁判：利傑在第 4 批之後，一個平衡數值都沒有動過，之後的變化全部來自使用者的設計決定。
5. **每輪試玩回饋**：先解釋原因，再提出 3–4 個用字母編號、可以組合的方向（使用者常會選「全部」或「C 加上 D」）。數值由主導者先提一個版本，並標明「這是我的提案，你可以改」。
6. **美術批次**：只改外觀時，模擬閘門必須和改之前一字不差（`--seeds 10 --summary` 加 `--cvc`）。這樣美術怎麼改都不花平衡的時間。
7. **CPU、輔助連段、學習型 CPU**：等規則穩定後再做。**規則還在改時不要開 dream-rsi 搜尋**：這次重新凍結了 3 次，每個搜尋單元都要三方合併再重新量一次。
8. **演出與過場**：最後做，先交文字分鏡定稿。

## 3. 角色建模注意事項

- **骨架固定**：21 關節的人形骨架，每個型態一個 `defbody`；比例用 `:props`（例如手臂 ×2.6）。
- **公平底線**：所有型態的受擊圓柱都一樣（r 0.38、h 1.8）。翼、光環、脖子都不加受擊範圍。漂浮只是畫的，受擊圓柱留在地面。
- **漂浮用 kit 的 `:lift`**，不要寫進自己的動作裡。共用的走路、Step、Hoho、受擊動作都以 root 0 播放，寫在自己動作裡的話，一移動就會下沉（決定 33）。地面高度要扣掉 `BODY-LIFT`，否則腿會被算短。
- **武器的命中點放在看不見的骨架手上，再把可見的武器畫過去**。不要把可見的武器直接掛在手臂骨架上，否則看起來就是「手臂變成翅膀」。
- **半透明部件**：引擎 alpha < 1 的路徑會畫出暗色幻影。改用自發光乘上本色（不用改 shader），本體 0.35、邊框 0.6。
- **會彎的部件**分節（翼 3 節），孔和鋸齒不要跨在關節上。
- **姿勢用 FK 解出來，不要手調**：給定爪子的目標位置，反解 flex、side、elbow（梟頭的爪擊就是這樣做的；RAVEN EDGE 有 `tools/pose-solve.py`）。長手臂貼近身體時，手肘要大幅彎曲。
- **畫出來的距離 = 判定距離**：每一個 J/K 都要通過 FK 測試（±0.15 m）。沒有命中範圍的招式（放軌跡）改用「投擲檢查」：S 幀時尖端要在招式的 `:reach`。
- **改站姿會移動命中點**：命中姿勢要自己設定脊椎、出招的手臂和兩個手肘，不要依賴站姿。
- **旋轉招式**：要轉一整圈，就放兩個相隔 0.0001 幀、yaw 差 360° 的關鍵幀，讓動作開頭和結尾都是 yaw 0、不會倒轉回去。匯聚目標要扣掉動作本身的位移和旋轉。
- **型態在衝刺途中切換**時，漂浮高度會跳一下，要用關鍵幀把它藏起來。
- **在過場中放大角色**：關節矩陣會自動帶上倍率，但凡是用公尺寫死的東西（翼長、腿、地面、閃光）都要手動乘上倍率。

## 4. 動作模組設計要點

- **每個型態用自己的幀數做自己的動作**。不要拿 KIN 的動作用 `:clip-s` 加速給 EN 用，那正是「看不出來」的原因（Jilliel 的遠程、梟頭的遠程都因此重做）。
- **每一招都有自己的輪廓，而且全身參與**：
  - 腳要跨步或前衝，身體要前傾、扭轉，頭和脖子也要跟著動。
  - 每招都有清楚的蓄力 → 出手 → 收招。
  - 一組連段的每一招方向要不同：左斬、右斬、十字；旋、逆旋、上撩；撕、剪、掠、回、俯衝。
- **關鍵幀寫成「指向」**：在每個關鍵幀的註解寫下翼或爪在胸部座標系的方位角與仰角，之後要調整時才讀得懂。
- **副部件也要參與**：其餘的翼依序匯聚到目標；出招前先振翅一次；武器尖端拖出軌跡（每個型態的軌跡要有區別：Jilliel 是玉色的單道弧，梟頭是金色的三道爪痕）。
- **同一招在不同型態要播不同的動作**，用 kit 的 `:clip-map`（例如 KIN 的三連改播翼的動作），招式名稱不變，模擬讀不到。
- **SP 與毀魂技**：蓄力要越來越強（抖動、拉弓），發射要有大幅後座，收尾要有一個代表性的動作（例如合翼宣判）。
- **驗證**：
  - FK 距離測試。
  - 模擬閘門一字不差。
  - 繪製時每幀不多配置記憶體（79195 探針：10 次繪製 160 B，也就是每幀 16 B，這是引擎查 ECS 的底線）。
  - 背後與側面兩個鏡頭的前後對照截圖。
  - 標明「只用數字檢查過，需要你親眼確認」。

## 5. 玩法系統的規劃概要與重點

利傑最後的形狀，可以當成之後設計多型態角色的參考：

- **基本型態**：一個身分清楚的招牌系統（狙擊架式：J 前躍連射、K 後撤射擊、Step 位移、L 開槍），讓角色「會動的狙擊手」而不是站樁。
- **覺醒後的兩種模式**用同一個按鍵切換：
  - EN（遠程）放置不帶傷害的軌跡。
  - L「轉身」讓軌跡實體化，同時往前衝。
  - 形成「放置 → 實體化 → 衝刺 → J」的連段，以及遠近之間的擺盪。主機測試要釘死連段的幀數算式，例如軌跡的硬直要 ≥ 衝刺加 J1。
- **資源經濟控制節奏**：每條軌跡消耗 3 點閃步，命中退還 4、被防退還 2，KIN → EN 消耗 10。CPU 要保留存量。
- **型態鏈**：基本 → Jilliel → 梟頭。第二段覺醒沿用同一套系統，只差一點數值（×1.1、退還 5、+1 f）。
- **每個新機制都要同時有**：
  - CPU 規則，機率依難度 EASY ≤ NORMAL ≤ HARD。
  - 對手的反射鍵（例如 `:opp-trace`：對手怎麼躲軌跡）。
  - 輔助連段的路線。
  - 學習型 CPU 的情境。
  - 用次數統計來量測。
- **感知落差**：既有的威脅偵測是照 ≤ 12 m 寫的。31 m 的直線攻擊要改成「點到線的距離」和實際命中窗，而且只限 `:x-axis` 招式，舊的對戰才會完全不變。
- **共用檔案只加「預設不作用」的掛鉤**（`:lift`、`:clip-map`、`:intangible`、`:assist-combo`、`CINE-SCALE`／`CINE-SLOW`／`CINE-PLACE`……）。證明方式：其他角色的對戰結果一字不差，cvc 參考對局也相同。
- **互動造成的 bug 是常態**：觸控把上滑讀成 Hoho、連段追擊、輔助連段讀到上一次衝刺的結束幀。每改一個規則，都用瀏覽器腳本實測一次手動和輔助連段兩條路。

## 6. 平衡與閘門

- 閘門結果不合格時，**回報，不偷調其他數值**。由使用者決定：「先試玩再決定」、接受例外，或「不用調整，玩起來夠強了」。
- 一個例外要同時寫進：AGENTS.md、設計文件、DEVLOG、commit 訊息，並引用使用者的原話。
- 只改外觀時，模擬閘門必須一字不差。過場長度改變時，以前會影響時長的統計；自 2026-10-08 起，**閘門時長已不含過場**（DEVLOG §134）。
- 125–210 s 的區間是含過場時量出來的。改成不含過場之後，中位數普遍少 30–60 秒，區間要不要調整由使用者決定。

## 7. 演出與過場

- **先交文字分鏡**：分成幾段、每段的幀範圍、機位（角度、距離、高度、焦距）、演員動作和特效。之後用「第幾鏡、第幾段」來溝通。
- **開場就把演員擺好位置**（`CINE-PLACE`），結束時不論播完、跳過還是中斷，都放回原位，對戰不受影響。
- **兩種畫面比例都要拍**：桌面版上下各有 9% 的黑邊，手機直式會加寬視角並把鏡頭往後拉。
- **可用的工具**：
  - `CINE-SCALE`：把角色畫大，例如「對手小、利捷大」。
  - `CINE-SLOW`：讓演員和特效放慢，腳本本身的幀照常前進。
  - 白底加剪影（`card :white` + `silhouette-black`）、負片與漫畫風格的停格。
- **節奏**：命中瞬間用慢動作，並且逐漸加速（1/5 → 1/3 → 1/2），再接爆發段；開場要留時間讓玩家看清楚。
- **除錯定格**：用 `79200 + f` 把過場停在第 f 幀拍照，做成截圖對照表。

## 8. 多 agent 分工

- 依「可以獨立進行」切批次，每批一個 worktree、一個分支、一個新的子代理，交一份精簡的任務說明（包含使用者的決定、命令、驗收數字、規則）。
- **合併時要檢查共用的槽位**：這次兩批都用了 `*LB-WF*` 的 [64]–[66]，主導者合併時把其中一批搬到 [68]–[70]。
- 子代理有時會「改進」掉使用者的決定（例如把金色從 #B89A5A 改成 #CDB47A）。合併前要對照決定清單檢查差異。
- 每次合併後，主導者自己重跑全部的測試和閘門。
