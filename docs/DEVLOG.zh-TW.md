# RAVEN EDGE 開發紀錄與技術思辨

這份筆記記錄做 RAVEN EDGE 時幾個比較關鍵的決定：遇到什麼問題、考慮過哪些做法、最後選了什麼、代價是什麼。英文技術文件（`ARCHITECTURE.md`、`ENGINE_API.md` 等）寫的是「現在長怎樣」，這裡寫的是「為什麼會長這樣」。

先說清楚一件事：文中所有 FPS 和毫秒數，除非特別註明，都是在無頭 Chrome 的 SwiftShader（CPU 軟體算圖）上量的。SwiftShader 比任何一張真的顯示卡慢很多，而且慢的地方也不一樣，所以這些數字只能拿來比較「改之前」和「改之後」，不能當成實際遊玩時的效能。團隊沒有在實體 GPU 上跑過，這點在最後的「已知限制」會再提。

---

## 1. 圖形 API：先走 GLES3，後來換成 SDL_GPU

題目本身限定了 SDL3。SDL3 有三條畫圖的路：SDL_GPU、SDL_Renderer，或者只拿 SDL3 開一個 OpenGL context、自己下 GL 指令。

SDL_GPU 是最現代的選擇，可惜 emsdk 4.0.12 內建的 SDL 是 3.2.4，這個版本的 SDL_GPU 沒有 web 後端，在瀏覽器裡根本建不起裝置。SDL_Renderer 可以用，但它是 2D API，沒有深度緩衝，要做 3D 動作遊戲就得自己排序所有三角形，不實際。

所以第一版的分工是：SDL3 負責視窗、GL context、輸入、計時和音訊，畫圖全部走 OpenGL ES 3.0（在 Emscripten 上就是 WebGL2）。整個遊戲先用這套做完。

之後使用者問「SDL_GPU 真的不能用嗎」。實測確認 SDL 3.2.4 的 `SDL_GetNumGPUDrivers()` 在瀏覽器裡回傳 0；SDL 3.4 也還沒有 WebGPU 後端，但有一個進行中的草稿 PR #16020。我們拿這個分支自己建 SDL，修掉幾個擋路的問題，把整個算圖層搬到 SDL_GPU，GL 程式碼全部刪除。來龍去脈寫在第 11 節。現在的代價是瀏覽器必須支援 WebGPU，而且依賴一個尚未合併的 SDL 分支。

## 2. 建置管線

### 2.1 Lisp → C → wasm

ECL 的特色是把 Lisp 編成 C。要跑在瀏覽器裡，C 這一段就交給 Emscripten。實際流程（`build.sh`、`tools/build.lisp`）：

1. 把 `engine/MANIFEST` 和 `game/MANIFEST`（當時是 `src/MANIFEST`）列的所有 `.lisp` 依序串成一個 `build/NAME/game-all.lisp`。
2. 用 **32 位元的 host ECL** 對這個檔案做 `compile-file :system-p t`，同時把 ECL 內部的 C 編譯器換成 `emcc`、`ar` 換成 `emar`。產出的 `.o` 已經是 wasm 物件檔。
3. `c:build-static-library` 包成 `libgame.a`，初始化函式叫 `init_game`。
4. `emcc` 把 `engine/c/main.c`（當時是 `src/main.c`）與其他 `.c` 檔、`libgame.a`、`vendor/ecl/` 下的 `libecl.a`、`libeclgc.a`、`libeclgmp.a`，以及 `vendor/sdl3-webgpu/lib/libSDL3.a` 連起來，WebGPU 的 C API 由 `vendor/emdawn/` 的 emdawnwebgpu port 提供，輸出 `dist/NAME/index.{html,js,wasm}`。

host 必須是 32 位元，因為 wasm32 的指標和 fixnum 都是 32 位元，ECL 在 host 上產生的 C 會把 fixnum 範圍之類的常數寫死進去，兩邊不一致就會出錯。ECL 原始碼裡 `INSTALL` 的「Cross-compile for the WASM platform」一節也是先建 `ABI=32` 的 host 版。

### 2.2 自己組一個靜態的 libecl.a

照 ECL 的說明做完交叉編譯，`build/` 目錄裡會有一個 `libecl.so`。我們一開始想直接連它，結果發現它其實是 Emscripten 的 SIDE_MODULE（檔頭有 `dylink.0` 區段），是給動態連結用的，而我們想要一個單純的靜態 wasm 執行檔。

解法是自己組：交叉建置的中間產物裡本來就有 `libeclmin.a`（C 寫的核心）、`liblsp.a`（編譯好的 Lisp 核心）和 `c/all_symbols2.o`（符號表）。`tools/vendor-ecl.sh` 把 `liblsp.a` 拆開，每個物件檔加上 `lsp_` 前綴免得撞名，全部塞進 `libeclmin.a` 的副本裡，得到 `vendor/ecl/libecl.a`（約 6.2 MB）。GC 和 GMP 則直接複製。

### 2.3 那個一定要加的 `-DECL_C_COMPATIBLE_VARIADIC_DISPATCH`

交叉建置的 `configure` 在 wasm 上自動加了 `-DECL_C_COMPATIBLE_VARIADIC_DISPATCH`（見 `build/config.log` 的 `CFLAGS`）。這個巨集會讓 `struct ecl_cfun` 和 `struct ecl_cclosure` 多一個 `entry_variadic` 欄位，並改成透過一個分派函式去呼叫可變參數的 Lisp 函式。原本是為了 ARM64 蘋果平台那種「固定參數和可變參數呼叫慣例不同」的架構設計的；wasm 的 `call_indirect` 會嚴格檢查函式簽章，所以也需要。

遊戲自己的程式碼如果沒加這個旗標，編出來的結構欄位位置就跟 libecl 對不上，執行時在 `call_indirect` 直接 trap，錯誤訊息完全看不出原因。現在 `build.sh` 的連結步驟和 `tools/build.lisp` 的 `c::*cc-flags*` 都有加，`build.lisp` 裡也留了註解。

### 2.4 為什麼全部串成一個編譯單元

正常的 ECL 專案會一個檔案一個檔案 `compile-file`，編 B 之前先 `load` A，讓 A 定義的 macro、struct、常數在編 B 時看得到。我們做不到這件事：大部分檔案都有 `ffi:clines` 或 `ffi:c-inline`，這些東西只在「編成 C」時才有意義，host 的直譯器沒辦法載入執行；就算先編好，編出來的也是 wasm 物件檔，host 載不進去。

最省事的做法是把所有原始碼接成一個檔案，一次編完。後果：

- MANIFEST（現在是 `engine/MANIFEST` 與 `game/MANIFEST`）的順序變得很重要，macro、struct、常數要先定義才能用。
- 編譯錯誤的行號是 `game-all.lisp` 的行號，所以每個檔案開頭都插了 `;;;; ---- engine/lisp/xxx.lisp` 這類標記。
- 所有 `ffi:clines` 會落在同一個 C 檔，C 的 static 變數要加模組前綴（`r_`、`au_`、`w_`……）以免撞名。
- 改一行就要全部重編。後面第 5 節會講到，這一度讓建置時間變得很難看。

`tools/build.lisp` 裡留了一句 `ponytail:` 註解，說明哪天編譯時間真的受不了，再拆成每個檔案各自的物件檔。

## 3. GC：整個專案最棘手的問題

### 3.1 問題

ECL 用 Boehm GC（bdwgc），它是保守式 GC：掃描堆疊、暫存器和資料段，看到像指標的值就當成指標。在 wasm 上，這個假設有兩個地方不成立。

第一，wasm 的區域變數不在線性記憶體裡，GC 掃不到。bdwgc 在 Emscripten 上靠 `emscripten_scan_registers()` 補這個洞，但 `src/bdwgc/os_dep.c` 裡這段只在定義了 `EMSCRIPTEN_ASYNCIFY` 時才會編進去，而且要連結時加 `-sASYNCIFY`。我們的 libecl 沒有用 ASYNCIFY 建置，所以 GC 在任意時間點觸發時，某個 Lisp 函式正抓在手上、只存在 wasm 區域變數裡的物件，可能被當成垃圾回收掉。

第二，資料段不會被掃描。`gcconfig.h` 在 Emscripten 下把 `DATASTART` 和 `DATAEND` 定義成同一個值，等於資料段長度是零。C 的全域變數如果指向 Lisp 物件，GC 看不到。幸好 wasm 版 ECL 的設定有 `ECL_DYNAMIC_VV`（見 `ecl-emscripten/ecl/config.h`），編譯好的模組常數向量（VV）會用 `ecl_alloc` 配置在 GC 堆上，由模組的 codeblock 物件持有（`src/c/read.d`），而 codeblock 又能從編譯出來的函式物件一路追到，不必靠掃描靜態資料段，所以 Lisp 程式碼裡的常數不受影響。

### 3.2 考慮過的做法

- **用 ASYNCIFY 重建。** 這是官方支援的路，但 ASYNCIFY 會改寫幾乎所有函式，讓它們能中途暫停再恢復，一般會讓 wasm 變大、執行變慢。而且 libecl、GC、我們的程式碼全部要重建。對一個需要穩定 60 Hz 的動作遊戲，這個代價不划算。
- **binaryen 的 `--spill-pointers`。** 這個 pass 會把可能是指標的區域變數溢出到線性記憶體的堆疊上，讓保守式 GC 看得到。同樣有效能代價，而且要對 libecl 和遊戲都做。
- **找一個「保證堆疊上沒有 Lisp 物件」的時間點才回收。**

前兩個我們沒有實際量過，是看了機制之後判斷代價太高。第三個在這個專案的執行模型下剛好成立。

### 3.3 決定：Lisp 執行時關閉 GC，只在幀與幀之間回收

瀏覽器的主迴圈是 `emscripten_set_main_loop`，每一幀呼叫一次 `NG::GAME-FRAME`（現在是 `ENGINE::%FRAME`），回傳之後 wasm 的呼叫堆疊就整個清空了。這時所有還活著的 Lisp 物件一定掛在某個根上：symbol、特殊變數、ECL 登記的根，不會只存在某個區域變數裡。

所以 `src/main.c`（現在是 `engine/c/main.c`）的做法是：

1. `cl_boot` 之後立刻 `GC_disable()`，然後才初始化遊戲模組。
2. 每一幀在 `ECL_CATCH_ALL` 裡呼叫 `GAME-FRAME`（現在是 `ENGINE::%FRAME`）。
3. 回傳之後，如果 `GC_get_bytes_since_gc()` 超過 24 MB，就 `GC_enable(); GC_gcollect(); GC_disable();`。

這套規則衍生出幾條紀律，寫在 `ARCHITECTURE.md` 的「The GC rule」：Lisp 裡永遠不准呼叫 `(ext:gc)`；C 的 static 變數如果存了 Lisp 物件，要用 `ecl_register_root` 登記（`main.c` 對 `frame_sym` 就是這樣做的）；每幀配置量要壓低。音訊回呼剛好也符合：它是在兩幀之間由瀏覽器事件觸發，而且完全不碰 Lisp 物件（第 7 節）。

### 3.4 驗證

最早的管線驗證程式 `tests/spike.lisp`（改用 SDL_GPU 後已刪除，它畫的是 GL 三角形）就是為了這件事寫的：每一幀配置大約 20000 個短串列當垃圾，另外保留一個每幀更新的陣列加字串，然後檢查內容有沒有被破壞，沒有的話不會印出 `CORRUPTION`。當初用它跑了 1440 幀確認可行。整理這份文件時我們又用現在的 `main.c` 在無頭 Chrome 重跑一次，跑到第 1680 幀：回收了 60 次，堆大小一直停在 32,501,760 位元組，沒有任何 `CORRUPTION`。

### 3.5 後果

- 一幀之內配置的東西在幀結束前都不會被回收。某一幀配置特別多，堆就會長大（`-sALLOW_MEMORY_GROWTH=1`，初始 128 MB）。早期 `world-init` 啟動時會一次配置約 50 MB，雖然第一次幀間 GC 就收掉，卻拉高了 wasm 堆的峰值；後來模型產生改成不逐三角形配置，啟動也拆成一步一幀、每步之後回收一次（`engine/lisp/app.lisp`）。
- 一次完整 GC 在約 32 MB 的堆上要幾毫秒，會造成一次小卡頓。遊戲中每幀大約配置 17～41 KB（見第 4 節），照 24 MB 的預算推算，大概每 600～1400 幀才回收一次。
- 這套做法依賴「主迴圈每幀回到瀏覽器」這個前提。哪天要用 pthread、或在 Lisp 裡等待非同步事件，就得重新想。

## 4. ECL 效能：浮點數裝箱是頭號敵人

ECL 生成的 C 大多很直接，但浮點數很容易被「裝箱」：包成堆上的物件，每個大約 16 位元組。對一個每幀要算幾千次向量的遊戲來說，這會變成大量垃圾，而且因為上一節的 GC 策略，垃圾越多，卡頓越頻繁。我們的做法是寫完熱點函式就去看 ECL 生成的 C，搜尋 `ecl_make_single_float`、`ecl_times`、`ecl_divide`。以下是一路踩到的坑（完整版在 `ARCHITECTURE.md` 的 Gotchas）：

- `single-float` 存進一般的地方（串列、沒宣告型別的 struct 欄位、`defvar`、一般陣列）就會裝箱，只有 `(simple-array single-float (*))` 和有宣告型別的區域變數不會。所以熱資料一律放在 f32 陣列裡。
- ECL 24.5 在 `(safety 1)` 下，連有宣告型別的 `let` 初始值都會用泛型的 `ecl_times` 算完再拆箱；陣列參數的型別檢查還會走很慢的 `cl_typep`。為此寫了 `defun-fast` 巨集（`package.lisp`）：進函式時做便宜的型別檢查，然後在 `(safety 0)` 下執行本體。型別錯了照樣會丟 `type-error`。
- 平行 `let` 如果遮蔽同名變數，會先把所有初始值算進裝箱的暫存變數，要改用 `let*`。
- 浮點數的 `min`、`max`、`abs` 在 ECL 24.5 是泛型呼叫，就算參數有宣告也一樣，`min`/`max` 還多了 NaN 檢查。熱迴圈裡改用 `ffi:c-inline` 呼叫 `fminf`、`fmaxf`、`fabsf`。
- `(incf (aref v i) x)` 會裝箱，除非 `x` 包在 `(the single-float ...)` 裡，要寫成 `(setf (aref v i) (+ (aref v i) x))`。
- 傳給非 inline 函式、或從它回傳的浮點數一定裝箱。熱路徑改成傳 f32 陣列（那些 `!` 結尾的函式），或宣告 inline。
- wasm32 上 fixnum 只有 30 位元（`CL_FIXNUM_MAX` 是 536870911），`(* seed 1103515245)` 這種線性同餘亂數會變成 bignum，每次呼叫都在配置記憶體。亂數改用 C 的 `long long` 算。

效果：`draw-mesh`、`m4-euler!`、`m4-mul!`、`fx-billboard` 每次呼叫配置 0 位元組；場景的 `world-update`＋`world-draw` 每幀約 1.2 KB；實際遊戲待機每幀約 17 KB，4 個角色打起來 20～25 KB，第 3 波 7 個角色加飛行道具是 30～41 KB。

## 5. 建置時間：從 2 分 18 秒回到 5 秒

有一陣子 `-O2` 建置突然要 2 分 18 秒。用 `emcc -O1 -c -ftime-trace` 對保留下來的 C 檔做分析，發現幾乎所有時間都花在同一個函式上：一個 1.7k 行、裡面有大量巢狀 `with-xform` 的場景建構函式。

原因是 `unwind-protect`、`handler-case`、`catch` 在 ECL 裡都編成 `setjmp`。一個函式裡的 `setjmp` 一多，控制流程就變成不可約（irreducible），clang 的 wasm 後端要先把它修成可約的（Fix Irreducible Control Flow），再做暫存器著色，兩者都是超線性成長。把大函式拆成小函式之後，建置時間回到 5 秒。

之後的規則是：`handler-case` 只在每幀最外層放一個（現在是引擎 `app.lisp` 的 `%FRAME`，啟動步驟另有一個 `%INIT-STEP`），大型建構程式碼要拆小。同一類問題還有一個變種：`EM_ASM` 不能出現在任何被 inline 進「有 `handler-case`／`catch`／`unwind-protect` 的 Lisp 函式」的地方，clang 會報「Cannot use EM_ASM* alongside setjmp/longjmp」。音訊模組改用 `EM_JS` 解決，因為 `EM_JS` 是 import，永遠不會被 inline。

## 6. 算圖

### 6.1 美術方向：程式產生的平面著色低面數模型

沒有美術素材，所有東西都要用程式產生，所以一開始就選了平面著色（flat shading）加頂點色的低面數風格。`meshgen.lisp` 提供方塊、圓柱、錐、球、刀等基本形狀，用 `with-xform` 組合，每個面的亮度隨機抖動一點（`:jitter`），看起來比較有手工感。頂點格式只有位置、法線、顏色共 9 個 float。

角色是「每個關節掛一個剛體部件」，一個部件一次 draw call，沒有蒙皮。這讓動畫系統簡單很多，也讓「打殘」變得很容易做：把手臂那幾個部件拆下來當碎片丟出去就好（第 8 節）。代價是 draw call 多，訓練場 4 個角色時 F3 顯示大約 103 次。

### 6.2 光源與後製

場景的樣子靠兩件事撐起來：雨夜的霧和霓虹。每幀最多 8 個點光源，挑離鏡頭注視點最近的；完全在視錐外的光源不佔名額。算圖先畫進一個多重取樣（MSAA 4x）的離屏目標，解析之後做 bloom 再合成到畫面上（GL 版用 FBO 和 `glBlitFramebuffer`，SDL_GPU 版改成 render pass 的 resolve，見第 11 節）。粒子、刀光、雨、貼花全部進兩個 fx 批次（加法混合和 alpha 混合），每批每幀 16384 個頂點。場景的雨和倒影甚至是 C 程式（現在是 `game/c/world.c`）直接寫進 fx 批次的 buffer，完全不經過 Lisp。

場景作者提出「每個 draw 要能有自己的鏡面反射強度」：地板想要 0.9 的濕亮反光，牆面只要 0.2，全域只有一個值只能折衷。引擎後來加了 `draw-mesh` 的 `:specular` 參數。

### 6.3 SwiftShader 量出來的數字要打折看

在 SwiftShader 上做效能分析時（以下是 GL 版時期的數字），有幾個結論和真 GPU 完全相反：

- 場景 demo 在 1280×720 下，8 個逐像素光源約佔整幀的 55%；bloom、天空、MSAA 各自不到 5%。場景 demo 約 9 fps，把場景光源關掉是 18 fps。
- 我們照直覺在 shader 裡加了 `if (d2 >= r*r) continue;` 想提早跳過沒照到的像素，結果在 SwiftShader 上毫無作用：它是在 CPU 上用 SIMD 模擬 GPU，分歧的分支兩邊都會執行。真 GPU 遇到一致的分支會跳過，所以這個提早跳出還是留著。
- 在 SwiftShader 上真正有用的是：減少迴圈次數、把工作移到頂點、減少像素。所以引擎加了 `*pixel-lights*`（只有最近的 N 個光源逐像素算，其餘改在頂點算，8 降到 1 可以省約 40%）和 `*render-scale*`（離屏解析度，0.7 大約讓整幀時間減半）。

這些知識最後變成動態畫質：`*auto-render-scale*` 打開後，每秒平均一次幀時間，超過預算（18 ms 的 1.25 倍）就降一級，先把解析度從 1.0 每次降 0.1 降到 0.7，再把逐像素光源降到 3、再降到 1；連續 3 秒有餘裕就升回去，而且有遲滯和退避，避免來回抖動。引擎預設是關的，這樣無頭截圖才會穩定可比較；遊戲本身在打磨階段已經在啟動完成時打開（現在是 `game/lisp/main.lisp` 的 `start-game`）。

實際遊戲在 SwiftShader 下大約 8 fps，每幀跑滿 6 個模擬步長，更多的積壓直接丟掉，所以無頭測試裡的遊戲時間大約只有實際時間的一半。Lisp 這邊每幀約 1.3 ms 模擬加 0.6 ms 排繪製佇列，瓶頸明顯在（軟體）GPU 上。

## 7. 音訊

一樣沒有素材，所以 26 個音效（包含雨聲和配樂兩個迴圈）全部在啟動時用 Lisp 合成：振盪器、包絡、狀態變數濾波器、延遲、殘響、和一組做太鼓、銅鑼、尺八的「樂器」。合成全部花 770～810 ms，樣本共 9.1 MB，存在 C 配置的記憶體裡；Lisp 那邊的暫存 buffer 在第一幀之後就被回收。配樂是 96 BPM、D 小調五聲音階的 8 小節迴圈（20 秒），渲染時多算 2.5 秒再折回開頭，鼓聲和殘響的尾巴才能無縫接上。

混音器是純 C，掛在 `SDL_OpenAudioDeviceStream` 的回呼上（F32、雙聲道、48 kHz、32 個聲部，最後過一個峰值限制器）。為什麼不在每幀由 Lisp 餵資料？

- 在 web 上，SDL 3.2.4 用 `ScriptProcessorNode` 的 `onaudioprocess` 事件驅動回呼，每次 2048 幀（約 43 ms）。JS 是單執行緒，這個事件只可能在兩幀之間觸發，不會打斷 Lisp。回呼本身也不碰 Lisp 物件，剛好符合第 3 節的 GC 規則。
- 遊戲卡頓、GC 或分頁切到背景時，音訊不會餓死，也沒有待補的佇列。
- AudioContext 不是 48 kHz 的裝置（例如 44.1 kHz），SDL 會自己重新取樣。

瀏覽器的自動播放限制：AudioContext 一開始是 `suspended`，要等使用者互動。SDL 3.2.4 自己有個計時器會在 `navigator.userActivation.hasBeenActive` 變成 true 後呼叫 `resume()`，但 Safari 要求 `resume()` 必須在手勢處理函式裡面呼叫。所以 `au_open` 另外在 `window` 上掛了 `keydown`、`pointerdown`、`touchend` 的 capture 監聽器，直接在手勢裡 resume。無頭 Chrome 預設不擋自動播放，要加 `--autoplay-policy=document-user-activation-required` 才測得到；這樣測時，第一次按鍵前狀態是 `suspended`，按下去之後是 `running`。

## 8. 玩法設計

設計規格在 `GAME_DESIGN.md`，背後的研究在 `research/ng4-notes.md`。研究筆記最後的結論有兩條直接變成了遊戲核心：

1. 《忍者外傳 4》最新的點子是「用量表變身來反制紅色攻擊」的猜拳關係（閃開，或花量表硬破）。
2. 打斷肢體會出現處決提示；用剛體部件做角色的話，這件事很好實作。

以下是幾個比較有意思的設計決定。

**判定形狀和動畫脫鉤。** 攻擊判定是寫死在攻擊者本地座標的幾何形狀（扇形 ARC、膠囊 CAP、球 SPH），不跟著動畫裡的刀走；刀的實際位置只用來畫刀光和火花。這樣平衡數值和動畫可以分開調，動畫師（其實也是程式）改姿勢不會改到難度。實作時還遇到一個插曲：規格裡照關節角度寫的攻擊姿勢，實際算出來刀都指向天空。後來寫了 `tools/pose-solve.py`，用和 `anim.lisp` 一樣的前向運動學反推手腕角度，讓每個攻擊關鍵影格的刀身方位角和仰角符合規格描述。

**60 Hz 固定步長。** 規格的所有幀數據都以 60 fps 的「幀」為單位，模擬也就用 1/60 秒固定步長跑，每幀最多補 6 步，積壓更多就丟掉。這讓「第 15 幀命中」這種描述在任何幀率下都成立。慢動作透過每個角色自己的時間倍率 K 實現，事件判斷用「是否跨過第 N 幀」，所以 K = 1 時幀數完全精確。

**hitstop 是全域凍結。** 命中停頓期間整個遊戲模擬停止（dt = 0），但粒子、鏡頭震動、UI 和雨照常跑。同一幀有多個停頓事件取最大值，不相加。這比「只凍結攻擊者和被打的人」簡單很多，也更有打擊感。輸入緩衝用的時間戳 `*tick*` 在 hitstop 期間照常前進，所以停頓時按的鍵會被記住。

**攻擊權杖。** 我們想要「很兇但公平」：近戰權杖只有 2 個、遠程 1 個，拿到權杖才能出招，沒拿到的敵人在外圈繞圈，偶爾做假動作。但玩家出了大硬直（≥ 14 幀恢復）時，附近的敵人可以拿第 3 個「懲罰權杖」，而且蓄力縮短為 0.8 倍。從鏡頭外攻擊的敵人蓄力多 10 幀，並在畫面邊緣顯示紅色箭頭。規格的第一條原則是「每一次被打中都是你自己的錯」，這些規則都是為了它。

**紅色攻擊。** 蓄力至少 48 幀（頭目第二階段 42 幀），蓄力期間有霸體，全部造成擊倒，擋了會破防加全額傷害。應對方式只有三種：閃避、在蓄力中用 Raven 型態的攻擊打斷（Raven Break），或在 Raven 型態下花 15 量表硬擋。

**打殘與 Obliterate。** 重攻擊把敵人打到 30% 血以下（OXHEAD 25%）就拆掉它的武器手，頭上跳出提示，按重攻擊一刀處決。殘兵不處理的話，3 秒後會發動紅色的 Death Grip 撲上來。系列作裡「斷肢的敵人會自爆式反撲」這點在研究筆記標為未證實，我們還是採用了，因為它會逼玩家主動去收尾。

**Raven 量表。** 打中 +2、重攻擊命中 +4、擊殺 +3、格擋和 Just Dodge 各 +8、Obliterate +25，不在 Raven 型態時每秒自然 +1。40 以上可以發動，Raven 型態每秒掉 10。規格估計每波可以變身 2～3 次、頭目戰 3～4 次。

**Just Dodge 的判定放寬。** 規格寫的是「閃避前 10 幀內碰到敵人判定」。但翻滾速度是 18 m/s，一個 2 公尺寬的攻擊弧大約 2 幀就穿過去了，實際上變成一幀的窗口。所以閃避期間用 `*just-dodge-reach*`（0.8 m）把玩家的受擊半徑放大來判定。

**原創名稱。** 研究筆記的原則是「照結構抄，名字自己取」。遊戲裡沒有用《忍者外傳》的任何角色、名稱或素材：主角是 REN，變身叫 Raven Form，量表叫 Raven gauge，Izuna Drop 風格的抓摔叫 Thunderfall，飛燕風格的飛身斬叫 Kestrel Strike，舞台是虛構的 Neo-Kasumi 市 Tsukuyomi Tower 頂樓，敵人是雨之軍團和 ENRA。

## 9. 團隊與流程

這個專案是由多個 AI agent 分工完成的，大致分成這幾個階段：

1. 第一階段三條線平行：引擎（平台、數學、算圖、模型產生、文字）、音訊、以及玩法研究和設計規格（產出 `research/ng4-notes.md` 和 `GAME_DESIGN.md`）。
2. 第二階段：戰鬥核心（動畫、角色、判定、玩家、特效、HUD）和場景（`world.lisp`）平行進行。
3. 第二階段 b：敵人 AI 與遊戲流程（`enemy.lisp`、`game.lisp`），同時另一條線做算圖效能。
4. 最後是審查、打磨和文件。

能平行做而不互相踩到，靠的是幾份事先寫好的「合約」：

- `ARCHITECTURE.md` 定下模組表（誰負責哪個檔案）、`MANIFEST` 順序、GC 規則和 C static 的命名前綴。
- `ENGINE_API.md` 把引擎的每個呼叫、座標慣例、「`!` 函式不配置記憶體」這類規則寫清楚，玩法那邊只照文件寫，不用讀 render 的原始碼。
- `world.lisp` 一開始先有一個 stub，只提供 `world-init`、`world-update`、`world-draw`、`arena-resolve`、`arena-ground-height`、`*arena-half*` 這組 API，戰鬥核心拿 stub 先開工，場景作者再把內容填進去。`WORLD.md` 的 API 表裡標了「added」的項目，就是後來在合約之外加的。
- 每個人用自己的 `NAME` 呼叫 `./build.sh NAME ...` 建測試目標，建置產物不會撞在一起。
- 發現對方模組需要改的地方，寫進文件的「Requests」或「Engine requests」段落，由負責人處理，而不是直接改別人的檔案。

另一個關鍵是無頭測試工具 `tools/run.mjs`。它不依賴任何 npm 套件，用 Chrome DevTools 協定開無頭 Chrome，照 JSON 腳本在指定秒數送按鍵、滑鼠和 `eval`，拍截圖，把 console 輸出轉出來，頁面有 JS 例外就回傳非零結束碼。配合遊戲裡的 `Module._debug_cmd(n)`（跳波次、強制某個敵人出某一招、在蓄力中凍結畫面、開無敵、自動遊玩 bot），agent 不需要真的「玩」也能驗證每個招式和每種敵人的行為。`*combat-log*` 會把狀態變化、命中、傷害、權杖都印到 console，測試腳本就對這些文字做斷言。`tests/shots/` 裡那些截圖都是這樣拍的。讓 bot 從標題一路打到結算畫面，全程沒有錯誤（最近一次的量測見第 13 節）。

這套做法也有盲點：agent 看得到截圖和 log，但感受不到手感。打擊感、鏡頭、難度這些東西，最終還是需要真人拿手把玩過才算數。

## 10. 已知限制與之後可以做的事

**畫面只在 SwiftShader 上比對過。** 截圖都來自無頭 Chrome 的軟體算圖。搬到 SDL_GPU 時曾在本機的 RTX 4090 上量過時間（見第 11 節），但無頭模式下用實體 GPU 拍到的畫布是空白的，所以實體 GPU 上的畫面沒有人親眼確認過，也不確定不同瀏覽器和顯示卡上有沒有相容性問題。

**libecl 是 `-O0` 建的。** 交叉建置時 `configure` 給的 `CFLAGS` 是 `-O0`，我們自己的 Lisp 程式碼則是 `-O2`。ECL 執行期函式（泛型算術、`format`、雜湊表等）都在跑沒最佳化的程式碼。用 `-O2` 重建 libecl 應該是投資報酬率最高的效能改善，順便也可能縮小 wasm（目前約 5.5 MB）。

**GC 會造成偶發卡頓。** 每次幀間 GC 是一次完整的 stop-the-world 回收，32 MB 左右的堆要幾毫秒。不用 ASYNCIFY 的增量回收，或是讓 ECL 用 shadow stack 記錄根，都是可以研究的方向，不過都不是小工程。

**動態畫質**在打磨階段已經預設開啟（見第 6.3 節）；它只在幀時間超出預算時才降低解析度。

**規格裡砍掉或簡化的部分**（詳見 `GAMEPLAY.md` 的 Cuts）：

- 鎖定目標（Tab 目前無作用）和威脅方向的自動轉鏡頭。
- Just Dodge 的殘影改成一團光。
- 圍巾用程式擺動，沒有彈簧模擬。
- 配樂只有一個迴圈，頭目第二階段是把它用 1.12 倍音高重新播放，沒有分層；雨聲音量也不會隨狀態改變。
- 頭目戰的 7 公尺鏡頭距離、橫移動畫、勝利時甩血的動作。

**文件裡還開著的請求**：第二層配樂（`GAMEPLAY.md`）。雨聲隨狀態調整、頭目戰 7 公尺鏡頭、模型產生不再逐三角形配置記憶體，都已在後續階段完成。

**SDL 的 WebGPU 後端還是草稿。** 我們固定在 PR #16020 的某個 commit，加上本地 patch。等上游合併、emsdk 內建的 emdawnwebgpu 版本跟上之後，應該換回官方版本，並把 patch 裡仍然需要的部分由人確認後回報上游（第 11.4 節）。有了 WebGPU，compute shader 和更好的多光源方案也變得可行。

## 11. 改用 SDL_GPU（WebGPU 後端）

### 11.1 先確認「不能用」是真的

第一版選 GLES3 的理由是 SDL_GPU 沒有 web 後端。被問到時先實測：用 emsdk 內建的 SDL 3.2.4 在無頭 Chrome 裡呼叫 `SDL_GetNumGPUDrivers()`，回傳 0，`SDL_CreateGPUDevice` 回報 `No supported SDL_GPU backend found!`。SDL 3.4 的後端也只有 Vulkan、Metal、D3D12。社群第一次嘗試的 PR #12046 在 2025 年 3 月被關掉；2026 年 7 月開的 PR #16020 支援 Emscripten，但仍是草稿。結論是官方版本確實不能用，只能拿草稿分支自己建。

### 11.2 一路上撞到的牆

1. **建立裝置會卡死。** 後端用忙等迴圈等 `requestAdapter` 的結果，瀏覽器裡這需要 ASYNCIFY 或 JSPI。作者的範例用 ASYNCIFY，但我們不能用：ECL 的 `handler-case` 底層是 setjmp／longjmp，會經過 JS 的 `invoke_*` 包裝，JSPI 無法跨越 JS 堆疊框暫停，ASYNCIFY 則會讓整個 ECL 變大變慢。最後的做法是讓網頁在 `preRun` 裡先用 JS 非同步要好 adapter 和 device，再開始跑 wasm；SDL 那邊加一段 patch，直接匯入這兩個物件。這樣建立裝置時就完全不用等待。
2. **ABI 不一致。** SDL 分支內附的 `webgpu.h` 比 emsdk 4.0.12 內建的 emdawnwebgpu 新，連 `WGPUTextureFormat_RGBA8Unorm` 的數值都不一樣（0x16 對 0x12），表現出來是「surface 不支援 SDR」這種莫名其妙的錯誤。改用 Dawn 2026-09-17 的 emdawnwebgpu 套件後，兩邊的列舉值就一致了。
3. **只有第一幀有畫面。** 後端只在會等待的 `WaitAndAcquire` 裡回收已完成的 command buffer；我們不能等待，只能用非阻塞的 `AcquireGPUSwapchainTexture`，結果 in-flight 計數卡在上限，之後每幀都拿不到 swapchain。修正是讓非阻塞版本在達到上限時先輪詢一次 fence。
4. **無頭測試環境。** 無頭 Chrome 預設的 WebGPU 在 SwiftShader 上會立刻回報 device lost，連純 JS 頁面也一樣，原因是 WebGPU 的 swapchain 和走 GL 的合成器之間沒有可共用的影像格式。改用 `--enable-features=Vulkan --use-vulkan=swiftshader --use-webgpu-adapter=swiftshader --use-angle=vulkan` 讓合成器也走 Vulkan 之後就正常了，這組參數現在是 `tools/run.mjs` 的預設值。
5. **ECL 的 `@`。** `ffi:clines` 和 `c-inline` 會把 C 字串裡的 `@` 當成自己的語法，WGSL 的 `@group`、`@location` 全被改寫壞。WGSL 因此都放在 Lisp 字串裡，當成資料傳給 C。

### 11.3 搬遷後的樣子

算圖層共有 11 條 pipeline（受光著色的四種變體、天空、兩種 fx、bloom 三段、UI）。每幀一個 command buffer：先用一個 copy pass 上傳四個緩衝，再畫 4x MSAA 的場景，接著五個 bloom pass，最後合成到 swapchain 並畫 UI。每次 draw 的資料不是逐次 push uniform，而是整批放進 storage buffer，由 vertex shader 用 instance 索引讀取；在 RTX 4090 上錄 258 次 draw，這樣做的 CPU 時間是 0.10 ms，逐次 push 則是 0.33 ms。`m4-perspective!` 直接產生 WebGPU 的 [0,1] 深度。

在同一套無頭環境下，兩個版本每幀的配置量都在 15～19 KB。實體 GPU 上兩者都卡在 vsync 的 16.7 ms，SDL_GPU 版每幀的 CPU 成本多約 0.15 ms。SwiftShader 下的畫面和 WebGL 版逐張比對，看不出差異（`tests/shots/gpu-*` 對 `webgl-*`）。

### 11.4 本地 patch 與上游

`vendor/sdl3-webgpu.patch` 裡每一處都標了 `raven-edge patch:`：匯入預先建立的裝置、非阻塞 acquire 也會回收 fence、`IndirectFirstInstance` 改成選用（SwiftShader 沒有，我們也用不到）、canvas selector 的長度欄位沒有初始化、bind group 沒變就不重設（錄 258 次 draw 從 0.55 ms 降到 0.03 ms）、SDL 不含 GLES 時跳過 WebGL 相關的掛鉤，以及 device lost 時印出原因。

SDL 專案的 `CLAUDE.md` 明訂不接受 AI 產生的程式碼貢獻。這些修正只給本專案用；如果要回報上游，必須由人自己確認問題、自己寫修正。

## 12. 最後的減法

功能完成後，照 ponytail 的原則（能刪就刪、標準函式庫有的不自己寫、只有一個呼叫者的層就拿掉）分三塊平行清理：引擎與工具、場景與遊戲流程、戰鬥。刪掉的主要是沒人用的東西：整套四元數 API、幾個輸入查詢函式、每個 mesh 都在算卻沒人讀的邊界、24 個多餘的 `:magnet 0`、重複的 guard、只在一處使用的包裝函式，以及可以由產生器重建的 JSON 腳本和舊截圖。為了 ECL 效能刻意寫成的熱路徑（`defun-fast`、`let*`、C 的 `fminf` 等）一律保留。每一塊清完都重新建置、跑數學測試、比對戰鬥 log 和截圖，並讓 bot 從標題打到結算，確認行為沒有改變。

## 13. 拆出引擎、改成 ECS，並整理成教材

遊戲完成後，使用者提出新的要求：把嵌在 Lisp 裡的 C 和 WGSL 拆成獨立檔案；核心邏輯改用函數式程式設計加 ECS 重構；可重用的架構獨立成引擎；整個專案要變成適合初學者的學習範例。工作分三個階段，每個階段結束都重新建置、跑主機測試，並讓 bot 從標題自動打到結算，確認行為沒變。

| 第二階段後 | 110.0～110.6 秒 | S | |

### 13.1 第一階段：拆檔、抽出引擎

原本的 `src/` 分成三塊：`engine/`（ENGINE 套件）、`game/`（RAVEN 套件）、`examples/`。

- **C 回到 C 檔。** 以前 C 程式碼寫在 `ffi:clines` 的字串裡，編輯器沒有語法高亮，編譯錯誤也很難對照。現在引擎的 C 在 `engine/c/*.c`，全部宣告集中在 `engine/c/engine.h`，場景的 C 在 `game/c/world.c`。Lisp 這邊只剩一行一個的 `ffi:c-inline` 呼叫。
- **WGSL 回到 WGSL 檔。** 著色器搬到 `engine/shaders/`，共用的部分（`Frame` 結構、光照、霧）用 `// #include "frame.wgsl"` 引入。`render.lisp` 的 `wgsl` 巨集在編譯時讀檔、展開 include、去掉註解，結果仍是編進 wasm 的字串常數：執行時不用讀檔，也照樣避開 ECL 對 `@` 的特殊處理（第 11.2 節）。
- **每個建置目標一份 MANIFEST。** `./build.sh DIR` 讀 `DIR/MANIFEST`，引擎的 MANIFEST 永遠排在前面，網頁標題取自 `# title:` 那一行。
- **引擎掌握主迴圈。** 啟動步驟、每幀流程、錯誤顯示、除錯指令佇列都搬進 `engine/lisp/app.lisp`，遊戲只用 `run-game` 登記自己的載入步驟和每幀函式。引擎的程式碼不再提到遊戲，`examples/engine-demo` 不帶任何遊戲程式碼也能建置。
- **補上 `tools/pkgcheck.sh`。** 分成兩個套件之後出現一種新的錯誤：遊戲用到引擎沒有 export 的函式名，會悄悄變成遊戲套件自己的符號，而 ECL 對未定義的函式不發警告。這支腳本只讀原始碼、不編譯，列出這種符號。

### 13.2 第二階段：ECS 與函數式核心

- **自己寫一個很小的 ECS。** `engine/lisp/ecs.lisp` 一百多行：實體是一個 fixnum（槽位加世代），每種元件一個長度 256 的向量，`do-entities` 展開成一個普通迴圈。沒有用現成的函式庫：需要的功能就這麼多，一個檔案寫得完，而且是純 Common Lisp，可以直接在主機上測（`tests/ecs-test.lisp`）。編號帶世代，是為了讓「記住別人的編號」這件事安全：實體刪掉後，舊編號自動失效。
- **什麼是實體，什麼不是。** REN、敵人、訓練假人、飛行道具是實體（以前的 `actor` 結構拆成 `transform`、`motion`、`model`、`health`、`fighter`、`blade-trail`、`player`、`brain` 等元件；飛行道具以前是一個 32 格的 float 池）。粒子、雨、碎片不是：它們有好幾千個，放在 float 陣列裡幾乎零成本，做成實體只會變慢。
- **規則是純函式。** 判定、命中結果、取消視窗、Raven 量表、攻擊權杖、分數評價都搬進 `game/lisp/rules.lisp`，只收參數、只回傳值。這個檔案是純 Common Lisp，`tests/rules-test.lisp` 在主機上一秒內就能跑完，不用建置也不用瀏覽器。
- **狀態仍然原地修改。** 系統（命令式外殼）收集規則需要的輸入、呼叫規則、再把結果寫回元件。沒有改成「每步產生新元件」，因為 ECL 會把存進一般位置的 float 裝箱（第 4 節），全部複製一份會讓垃圾量和 GC 停頓成倍增加。
- **事件取代直接呼叫特效。** 戰鬥程式碼改成 `emit` 事件，`feedback.lisp` 的 `feedback-system` 在每個步長結尾統一播放聲音、血霧、震動、停頓和慢動作。hitstop 和慢動作在步長結尾設定、從下一步生效，時序和以前規則直接設定時一樣。
- **資料集中。** 招式（`moves.lisp`）、角色外觀（`bodies.lisp`）、動畫（`clips.lisp`）、音效（`sounds.lisp`）都是宣告式的資料檔，平衡數值集中在 `tuning.lisp`。函式也順便改了名，例如 `actor-start-move` → `start-move`、`make-enemy` → `spawn-enemy`、`hit-feedback` → `emit-hit` 加 `feedback-system`（`GAMEPLAY.md` 已全部改用新名稱）。

代價：同一段自動遊玩，**每秒真實時間的配置量多了約 10%**。規則回傳的結構和事件串列都是每次命中新配置的短命物件。**啟動完成時的堆從 71 MB 變成 87 MB**，但實際增加的只有模組載入時的 1.8 MB 常數資料：它剛好越過 Boehm GC 的一個堆擴張門檻，堆一次長了一大格。兩項都還在預算內。

### 13.3 第三階段：教材

- **`examples/hello`**：123 行、讀得完的最小遊戲。用到 `run-game` 的載入步驟和每幀函式、`build-mesh`、鏡頭、三種元件、三個用 `do-entities` 寫的系統、一條純規則、一個事件、鍵盤輸入、UI 文字和一個合成音效。它刻意不用固定步長和 `defun-fast`，改用真實 dt 和一般的 `defun`，讓第一次讀的人只需要面對 ECS 的概念；什麼時候需要那些工具，教材第 3、8 步會講。它啟動完成時的堆是 23 MB，wasm 4.8 MB（大部分是 libecl）。
- **`docs/TUTORIAL.zh-TW.md`**：從建置、專案地圖、逐行讀 hello，到幀迴圈與 GC、ECS、純函式規則、事件、算圖，最後追蹤 RAVEN EDGE 的一下攻擊從招式資料到音效的完整路徑，每一步都標了檔案和行號，最後附練習題。
- 根目錄 `README.md` 改寫成入口頁；`ARCHITECTURE.md`、`ENGINE_API.md`、`GAMEPLAY.md` 更新到新的程式碼，刪掉已經不成立的敘述。


### 13.4 第四階段：獨立審查

另開一個 agent 只讀不改，把原本的 `src/`（第一階段前的備份）和新程式逐項對照：資料檔逐條比對、抽出來的 C 對照原本的字串、WGSL 去掉註解後比對、`emit` 和 `feedback-system` 的參數逐一核對、在 host 上編譯每個目標檢查有沒有未定義的函式。重構本身沒有造成嚴重的行為差異，但查出一個**原本就有**的錯誤：

- **按住防禦幾乎每次都變成彈反。** 防禦按鍵的時間戳記用的是 `*ptick*`（1/16 幀），判斷彈反視窗時卻拿 `*tick*`（幀）去減，差出來永遠是很大的負數，永遠落在 8 幀的視窗內；防連打的 20 幀判斷也因為單位錯了而從不觸發。改成兩邊都用 `*ptick*` 換算幀數之後，重跑同一個腳本（訓練模式，敵人攻擊，Q 從第 8 秒按到第 24 秒）：原本 0 次格擋全是彈反，改完 9 次格擋、0 次彈反，防禦量表耗盡會破防，跟設計一致。
- 敵人屍體留存時間 2 → 2.5 秒：重構後投射物命中要靠丟出者的實體還在，而爆裂苦無飛行加引信最長約 2.4 秒。
- `do-entities` 寫錯元件名稱現在會在編譯時報錯（原本會悄悄註冊一種新元件）；C 的隱式函式宣告改成錯誤（`-Werror=implicit-function-declaration`）。
- 修正文件：`c-inline` 的 `#` 後面是一個 36 進位的字元（第 11 個參數寫 `#a`），不是「只能到 `#9`」；教材裡幾處行號、頂點緩衝的描述。

最後一次完整自動遊玩：`game -> RESULTS (wave 4, run 114.5 s)`，無錯誤。

## 14. 用第二種類型的遊戲驗證引擎

RAVEN EDGE 完成、引擎也拆出來之後，一個問題還沒有答案：這個「引擎」到底有多通用？只有一款遊戲用過的引擎，很容易長成那款遊戲的形狀。使用者的要求是做第二款、類型不同的遊戲：1 對 1 的 3D 競技場格鬥 SOUL DUEL，參考《BLEACH: Rebirth of Souls》，指定山本元柳齋與更木劍八（非商業的同人練習，素材全部由程式產生）。目的有兩個：做出一款能玩的遊戲，並用它找出引擎的缺口、補上，最後把兩款遊戲都用得到的東西收回引擎。設計與招式表在 `DUEL_DESIGN.md`，操作與測試在 `DUEL_GAMEPLAY.md`，教材在第 9 步。

### 14.1 流程

1. **研究。** 先把 RoS 的系統（靈子與魂魄、30% 變紅、Kikon、猜拳三角、Hoho、覺醒）和兩個角色的設定整理成筆記，每一條標上「有來源」或「推測」。例如 RoS 的山本覺醒其實是強化始解，不是卍解；用卍解當覺醒是我們自己的選擇。
2. **引擎缺口稽核。** 另一個 agent 只讀不改，對照格鬥遊戲的需求逐項檢查引擎，列出 20 個缺口（多手把、每個玩家的輸入緩衝、火焰粒子、亂數種子、回合重置……）、可以直接沿用的部分，以及建議的施工順序。結論是：算圖、模型產生、動畫、ECS、音訊都能直接用；缺的是「不止一個人」相關的一切，和火焰特效。
3. **設計辯論。** 主持的 agent 先寫一份草稿，再交給兩個角色相反的評論者：一位格鬥遊戲設計師，指出草稿缺的是「決定遊戲能不能玩的數字」（擋下後的幀數優劣、揮空的硬直、轉身速度與追蹤、連段上限、完美 Hoho 的判定窗），並把系統數量砍半；一位技術主管，指出很多引擎工作可以留在遊戲裡、第一階段只准做「不改變 RAVEN 行為的加法」，並估了粒子、配置量、堆大小的預算。兩份意見合併成 design v1，當作所有 agent 的合約。
4. **分工平行開發，每個檔案只有一個主人。** 美術（身體、動作、音效、場景、特效，外加兩個瀏覽用的測試目標 duel-view 與 duel-vfx）、玩法（規則、操作、角色資料、系統）、引擎各一個 agent。美術與玩法之間的合約是動作的名稱：角色資料寫 `:clip :ya-q1`，美術就必須做出這個名字；還沒做好的動作會退回站姿並印一行 `missing clip`，所以玩法不必等美術。
   **引擎 agent 在另一份複本裡工作**（`ai-cl-game-test-engwork`）。原因是 `build.sh` 一開始讀引擎的 Lisp，幾分鐘後連結時才讀引擎的 C：如果有人在同一棵樹裡改引擎，別人正在跑的建置可能會壞掉，更糟的是悄悄地用到一半新一半舊的引擎。所以引擎在複本裡改、驗證完再整批同步回來。它的驗證包括：先量出 RAVEN 截圖本身的雜訊（同一個執行檔跑兩次，差多少像素），之後把新舊引擎**同時**執行再比對截圖；以及 RAVEN 的每幀配置量不能變差超過 10%。
5. **引擎兩輪補強。** 第一輪（E）在開工前做設計裡列好的項目；第二輪（E2）處理美術與特效 agent 在開發中撞到的 15 個缺口（見 14.2）。
6. **審查。** 兩個只讀不改的審查：程式碼審查（55 項，其中 9 個 bug、11 個風險），以及一位格鬥遊戲設計師的試玩審查：用除錯指令跑 60 場固定種子的電腦對戰並寫小程式分析戰鬥紀錄，再用腳本模擬真人按鍵，列出 22 個問題。
7. **修正回合。** 兩個修正者分別負責玩法與 HUD，檔案不重疊。
8. **節奏決定**（14.3）。
9. **收成（harvest）。** 最後一個 agent 在主樹上把證明是通用的東西搬進引擎，同時刪掉兩款遊戲裡的副本。每搬一步都跑一場固定種子的電腦對戰，比對結果那一行和八行 `duel hash` 必須一字不差；RAVEN 則比對 ECL 產生的 C：664 個函式完全相同，不同的只有預期中改了呼叫的地方。

### 14.2 格鬥遊戲找到的引擎缺口

「E」是開工前的第一輪、「E2」是開發中的第二輪、「收成」是最後搬進引擎的部分。

### 14.3 開發中改變的設計決定

**節奏。** 設計的目標是固定種子的電腦對戰每場 120～180 秒。唯一保留的調整旋鈕是「靈子低於多少變紅」（`*red-threshold*`，設計值 0.30）。

- 第一版 AI 讓山本對劍八只打了約 38 秒：以 14 幀的反應延遲，每一招都來不及反應，而且電腦從不主動防禦。
- 加上近身防禦、出招節奏、挨打後「退讓」一段時間等規則，並把變紅門檻降到 0.20 之後，60 場的中位數是 YY 172.8、YK 136.0、KK 130.4 秒，在目標內。
- 審查推翻了這個結果。程式碼審查發現防止拖台的 heat 永遠不會歸零（造成傷害時歸零的那一步，下一個系統又加回 1），整個節奏是在這個 bug 上調出來的。試玩審查發現對局其實是「Breaker 迴圈」：Breaker 是每種組合裡最常出的一招，它的出招間接造成 50～73% 的傷害，但破防之後電腦**什麼都不做**（破防的追擊傷害是 0）；山本從不放火（60 場裡不知火 0 次、獄焱 2 次），因為不知火的距離區間幾乎到不了，電腦也按不滿蓄力；劍八為了拉長比賽被調得很被動。
- 修正回合重做了 AI：破防與崩架後追擊、被擋的收招不經延遲就反打、面對 Breaker 改用 Hoho／遠距離 Q1／往旁邊跨步，Breaker 衝刺的追蹤從 180°/s 降到 120°/s，山本在 7～9.5 公尺壓制、遠距離把不知火蓄滿、對手倒地時用滿蓄力的不知火把 Inferno 灌滿進入獄焱，劍八恢復設計上的積極。結果：Breaker 相關傷害降到約 25% 以下，破防後 90 幀內追擊成功 80～86%，山本每場放不知火 1.6 次（YY）、獄焱 1.7 次。
- 接著掃變紅門檻：0.10 到 0.30，三種組合的中位數只差約 10 秒（0.30 時 YY 94、YK 81、KK 95 秒）。原因是 AI 現在一抓到破綻就接 Kikon，門檻高低幾乎不影響要打幾次。所以留下設計值 0.30，但比賽太短。
- 主持者的決定：魂魄從 6 改成 9（這正是 RoS 的數字），靈子從 1000 改成 1100。最後的 60 場：YY 129.7、YK 106.9、KK 134.8 秒，全部 K.O.。

**防禦量表變成卍解的經濟（guard v3，2026-09-26）。** 使用者覺得山本還是不平衡，要求卍解的防禦量表不再自己回，只在打中對手和熄火之後回；也要求所有角色在維持防禦時量表不回，並取消西「按住 U = 霸體」。做法：卍解的量表每從對手身上真正扣掉 1 點靈子就回 0.1（燙傷、Kikon 不算），歸零熄火後照舊用計時回滿再「REIGNITE」，Kikon 重置時沿用不補（使用者選的）；東的反衝不變，所以連續被擋 8 串才熄火，打中一串就補回一串。防禦中量表不回，而且等待回復的延遲是「暫停」不是「重算」，因為手機上拇指停著就是防禦，重算會讓「拖、停、拖」的走位永遠回不了量。西的 U 改成一般防禦加「殘日獄衣」：擋下只扣一半、每一下被擋的近戰都燙傷對手（Quick 5、其他 15，Quick 燙得少是為了不讓電腦的 Q1 重置被刷燙傷），使用者另外要求西對所有遠程攻擊減傷到 0.6 倍並且不被打出硬直（南的束縛還是會綁住：那是抓，不是硬直）。這樣「U 在每個型態都是防禦」，手機版也不需要「鎖住 U」的手勢了。同一批：野晒二杯停手 3 秒後才以每秒 1.5 掉（原本 1 秒後每秒 3），全體靈子 1100 → 1300（使用者的理由：真人對戰比電腦對電腦快很多，電腦對戰長一點沒關係），所以測試關卡的中位數範圍從 125～180 秒放寬到 125～210 秒。平衡：設計在 1200 靈子量到的「東受傷 1.4 → 1.3」在 1300 不夠，改成 1.2；40 個種子裡山本對劍八從 13 勝升到 17 勝，剩下的差距在兩邊都還沒覺醒的階段，這一批的旋鈕碰不到。同一天使用者看完又追加一刀，刻意削弱山本：卍解的防禦量表每次被削減都 ×1.3（兩種架式都算，西的火衣減半之後實際 ×0.65），東打人時的回復量從 0.10 減半為 0.05（西維持 0.10，改成每個架式各自的 `:feed`），東連續被擋的串數從 8 串降到 5 串就熄火。同時把劈開隕石、一口喝乾、ぶった斬る、撫斬這些「刀身接著一道斬線」的招式分成兩段：受擊者離出招者在該型態 Q 的距離內算刀身（近戰），之外才算斬線（遠程），用同一個判定窗依距離決定，所以一刀不會打到兩次。使用者明說這是刻意的削弱，不調其他數值補回來。

**決定性。** 一開始就決定慢動作用「跳步」：每一步累加慢動作倍率，累積滿 1 才跑一個模擬幀，所以幀數永遠是整數，同一個種子在任何幀率下都跑出同一場比賽。修正回合又補上四件事：命中停頓從表現層（feedback）移到規則（combat），因為它是模擬的時間；真人搖桿改用模擬擁有的視角方向換算，不再讀跟著真實時間平滑移動的攝影機；跳過過場改成「下一個步長才結束」，讓過場的 `:after` 也在模擬裡執行；過場結束時忘掉期間按下的鍵（原本在選單按 J 確認，會在開打第一幀變成一記 Q1）。

**其他修正回合的改變。** 連段在被擋時只能在收招最後 3 幀接（`*chain-lead*`），並把擋下的硬直公式改成精確值（原本每一招的實際優劣都比招式表差 1 幀，現在有除錯指令 2315～2318 直接量）；Q Q → F 的分支用新的 `:enter` 鍵從 F2 的第 8 幀（劍八第 6 幀）開始，才接得上；飛行道具被擋固定 14 幀硬直；互砍致命時兩邊的 Soul Break 在步長結束一起結算，雙方同時沒命就是平手；一方對另一方造成的凍結等兩個人都走完才生效。

### 14.5 還沒解決的問題

- **成對鏡頭沒有收回引擎**：只有 SOUL DUEL 用它。
- **延伸目標後來補上了**：Burst Reverse（Shift+J，2 格靈壓，連段第 2 下之後才能用；在兩個人都走完這一步之後才生效，所以同一步按下的 Kikon 一定贏；Kikon 改成突進之後，Burst 在命中結算前生效，突進還沒砍中就能用 Burst 逃掉）、衝刺（按住 Step，跳完接著跑，跑步中可以直接出招並帶 1 公尺的慣性）、對電腦時預設的 P1 背後鏡頭（模擬自己保存視角方向，換鏡頭不會改變電腦對戰的結果）。電腦也會用：被連段時照難度機率爆發，離太遠時衝過去（劍八比較常用），山本太近時往後衝回自己的距離。
- **Kikon 改成 RoS 的做法**（使用者要求）：以前 Kikon 鈕只在「打中已經變紅的對手」之後有效，按下立刻結算。現在按 O 是 Kikon 突進：紅色氣場 5 幀、以 16 m/s 衝最多約 6 公尺、1.6 公尺內出刀（S8 A3 R24，70 點，被擋 −14）。對手沒變紅時這一刀能被擋、只是一般命中；變紅後擋不住（閃步、Hoho 的無敵幀還是躲得掉），而且要在**砍中的那一步 O 還按著**才會變成 Kikon（`kikon-confirm-p`），先放開只是一般的一刀，打到 0 就是一般的 Soul Break。按著與否在模擬步裡讀 vpad，所以重播不變。結算從按鍵當下移到命中結算的最後（`settle-souls`，和 Soul Break 一起），剩下的角色過場沒動。動畫沒有新做：突進借用共用的跑步動作，出刀借用各自現成的一刀（`:clip-s` 讓借來的動畫仍在第 S 幀揮到）。電腦只對變紅的對手突進，並按住到出刀之後；自己沒紅時看到突進就防禦。測試關卡三組中位數 YY 153.4、YK 136.9、KK 140.6 秒（之前 144.2／138.1／140.8），沒有調任何數值；參考紀錄變成 `winner P1 konpaku 2-0 ticks 9780 secs 163.0`。
- **動畫和招式幀數的對齊只用眼睛看過**：duel-view 的動作條目每招只畫 4 格。程式碼審查列出的不一致還在，例如 `:ya-kaka` 的動畫 70 幀、招式 61 幀，`:ya-sig` 66 幀對 67 幀，`:ya-shiranui-throw` 第 6 幀才揮到、火球第 2 幀就出去，`:ke-flurry` 的動畫第 4 幀就砍、第一刀判定在第 10 幀。審查建議用 `clip-mark` 寫成自動測試，還沒做。
- **卍解時場景遠處的火還在燒**，設計說所有火焰都被吸進刀裡；卍解過場的鏡頭也還是偏向山本的背面。
- **節奏**：加了 Burst Reverse 之後三組中位數都落在 120～180 秒內（YY 134.2、YK 120.1、KK 135.8 秒；之前 YK 只有 106.9 秒），調的是電腦爆發的機率（NORMAL 0.6）；YK 剛好壓在下緣。

## 15. 手機單手模式與 PWA（2026-09-26）

使用者的要求：「幫我做一個簡單的『手機單手直拿模式』，並以 PWA (Progressive Web App) 建構出近似應用程式的體驗」。設計早就定好了（[DUEL_MOBILE_DESIGN.md](DUEL_MOBILE_DESIGN.md)），這次只做它的 P0（能玩的粗略原型）加上 P3 裡的 PWA 部分，做了什麼、哪裡偏離設計都記在該文件的 §12。

**觸控只是 vpad 的另一個輸入來源。** 引擎在 `pf_pump` 把手指事件連同 SDL 時間戳記排成一列交給 Lisp，`engine/lisp/touch.lisp` 的辨識器把它們變成點擊、靜止、撥、拖；遊戲端把這些寫進 P1 的 vpad。所以規則、AI、三組電腦對戰的雜湊（G2）完全沒變，RAVEN 的畫面逐位元相同（G1）。辨識器只看事件的時間戳記，不看幀數；在 `--fixed-dt` 下 SDL 的時鐘跟著虛擬時鐘走，所以同一段觸控腳本跑兩次，雜湊與戰鬥紀錄逐行相同，這就是設計要求的第二道決定性檢查。

**過程中改掉的幾件事。**
- 觸控的 `pointerdown` 不算「使用者啟動」（HTML 規格只認 `pointerup`／`touchend`），所以歷史紀錄陷阱和 Android 全螢幕要掛在 `pointerup`，否則 Chrome 會拒絕。
- 選單上的點擊一開始會被辨識成 Quick 並一直留在待處理的脈衝裡，進場第一步就出拳；現在不在對戰中時，每幀把待處理的脈衝清掉。
- 文字下限（每個字至少 11 CSS px）讓 390×844 的畫面上計時器和中間的量表標籤疊在一起；最小的修正是直式時計時器移到量表下面、標籤縮一半。鏡頭沒改，背後視角在直式下已經看得到兩個人。
- service worker 沒有照原本「index.html 走網路優先」的想法做：那樣可能拿到新的 index.html 配舊的 index.js／index.wasm。改成同一個版本的快取全部快取優先，`build.sh` 把建置的雜湊寫進 `sw.js`，新版裝好接手之後頁面自動重新載入一次。

**還沒做、還不確定的。** 沒有在真的手機上試過：誤判率、拇指搆不搆得到、幀率、返回手勢、iOS 背景之後 GPU 會不會掉，都等使用者用兩支手機回報。啟動時的 GC 堆從 55.4 MB 變成 87.1 MB（仍在 110 MB 預算內，wasm 記憶體沒變）；RAVEN 同一個執行檔也會在 57 和 71 MB 之間跳，看起來是 Boehm 堆成長的門檻，不是多了資料。

### 15.1 真機試玩後的調整（2026-09-27）

使用者在兩支手機上試玩：單手打完 NORMAL 一場、幀率順、返回手勢會暫停、螢幕不會暗、左手鏡像和離線啟動都正常。問題有兩個：「步法和 K 非常難分開，非連擊中上撥幾乎會觸發步法而不觸發 K」，以及「整體按鍵位置應該要往上，手勢操作的接受範圍也要再擴大」。

**為什麼上撥會變成步法。** 拇指一離開 10 px 的容許範圍，拖曳搖桿就開始作用，而且在「等放開確認 F」那段時間也一直有效。真的撥一下，拇指通常會滑 60–140 px，遠超過 28 px 的門檻，所以站著的時候角色先往前走，滑過跑步圈（1.6 × 48 = 77 px）就按住了 Step：角色跳一步（24 格，中途不能取消），等手指放開時 F 被塞進緩衝，然後就過期了。放開得比 80 ms 慢時，連 F 都不算，只算拖曳。右手拇指往上撥時自然會偏左上，超過 45° 就被當成往旁邊撥。連段中不會發生，因為出招時不看搖桿也不看 Step。

**改法（`engine/lisp/touch.lisp`）。** 新增「未定」狀態：離開容許範圍之後，撥的判定時間（120 ms）還沒過之前，搖桿讀 0，也不按住 Step；時間過了才變拖曳，中途越過門檻就是撥。等待放開確認 F 的那段也一樣不動。`up-lift-ms` 從 80 改成 150 ms，新增 `up-cone`，往上的判定放寬成左右各 60°。代價是慢慢拖的時候，角色晚最多 120 ms 才開始走。

**按鈕（`duel/lisp/onehand.lisp`）。** 所有圓鈕往上移 100 px；手勢區從 260×194 擴大成 342×410，把圓鈕那一欄也包進去。按下的點落在圓鈕的判定圓裡就是按鈕，其他地方都是手勢；手勢滑過圓鈕不會變成按鈕。

**驗證。** `touch-test` 41 項全過（新增：站著長距離上撥、斜上撥、慢拖、圓鈕邊緣）；`duel-touch.json` 多了一個 140 px 的上撥，記錄裡是 F 而不是 step，跑兩次雜湊一致；桌機的 G1、G2、smoke 都通過。

## 16. 山本卍解重製與防禦量表變慢（2026-09-27）

使用者重新規定了卍解：U 從『東・旭日刃』切到『西・殘日獄衣』；東是「1 倍傷害加上 0.1～0.5 倍穿透、1.5 倍受擊」，西是「霸體、完全抵擋（效果等於防禦、可被破防）、同時能做其他動作，但出 SP1 與 L 以外的攻擊就回東」；西的 SP1 反擊成功時回滿防禦量表；兩邊各有一招新的 L。設計文件（[DUEL_YAMA_REWORK.md](DUEL_YAMA_REWORK.md)）列了八個問題，使用者全部採用建議值：量表越滿穿透越高、打中和被擋都有穿透、西 360°、破防招把西打回東、U 不能取消東的收招、刪掉 ×1.3 的卍解削減、西的招架揮空仍然霸體、拿掉西擋近戰時的燙傷。同一天使用者也要求「大幅減少防禦量表的恢復速度」，所有角色每秒 12 → 5.5、破防後 14 → 6.5。

**砍掉的比加的多。** guard v3 的整套「餵火焰」經濟（打中回量表、東的反衝、×1.3 削減、熄火 BURNOUT、重置沿用、覺醒補滿）、西的火焰防禦（減半、燙傷、遠程 ×0.6 霸體）、L 切換、西自己的 J／K 一整組招式和動畫都刪掉了；新增的只有幾個通用的 kit 鍵：`:guard-to`（按 U 換型態）、`:drop-to`／`:keep`（出招先換型態，在招式第 0 格換，被拒絕的指令不換）、被動 `:ward`（`defender-state` 回報 `:guard`，360°，擋下時跳過防禦硬直）與 `:pierce`（`pierce-rate`，打中乘 (1+k)，被擋時 k 倍當作削血穿過去，沿用「削血不致死」）。規則檔還是不出現角色名字。「西不回量表」不用新程式：GUARD HOLD 本來就有「防禦中不回、延遲凍結」，只要把西算成防禦中。

**平衡靠執行期旋鈕掃。** 為了不必每次重建，加了除錯指令 20000+k／21000+k 直接改 `*ward-mult*`、`*pierce-max*`，同時開四個無頭瀏覽器跑種子測試。規格值（穿透 0.5、西 ×1.0）讓 YK 中位數掉到 123.6 秒，比 125 秒的下限還短；西越耐打（×0.8）山本越常贏（13/20）。最後 `*pierce-max*` 0.45、`*ward-mult*` 1.1：YY 128.6、YK 129.9（山本 10／劍八 10）、KK 169.2 秒，60 場全部 K.O.。二十場的勝場數本身有 ±2 的雜訊，所以選的是「兩個目標都落在範圍內的那一組」，不是算出來的最佳值。

**電腦怎麼對付一直待在西的山本。** 設計裡最擔心的是西「全擋、沒有硬直」讓電腦攻不進去、比賽拖過 300 秒。解法是讓劍八的破防反射（對手防禦超過 24 幀就在 3 公尺內出 I）把西當成一直按著的防禦：YK 二十場西被打破 48 次，其中只有 1 次是量表歸零，其他都是破防招。電腦的山本則把原本的「防禦」機率當成「切到西」，量表低時就留在東退開等量表回來。

**還沒解決的。** 電腦很少用焦熱地獄（YK 二十場 5 次），因為它只在「西剛擋下 3 公尺內的攻擊、L 可用、再擲一次 0.35」時出手；真人應該會常用。焦熱地獄的火柱直接沿用炎熱地獄的外觀（火柱環半徑改成 2 公尺，3 公尺的空心環打不到貼身的對手）。旭光和焦熱地獄共用 L 的冷卻格。都還沒有真人試玩過。

## 17. J／K 連段、O 收尾與「攻勢」（2026-09-27）

使用者的三個要求：J／K 要有角色特色、能組成輕重混合的連段，K 傷害高但慢、當起手會被 J 搶先、當收尾被擋會有大破綻，而且起手真的碰到對手（打中或被擋都算）才出後續，否則只揮一刀加硬直；連段完整打完可以接 O 擊退，按住 O 接毀魂技，只有對手血量低時必中；另外要有一個獎勵積極進攻的系統，防禦量表越少、越積極，拿到的資源越多。設計文件（[DUEL_STRINGS.md](DUEL_STRINGS.md)）問了九題，使用者全部採用建議值，並更正第四題：「JJ、JK 不代表真的只打兩下」。之後又加了一條：「K J 不要來回交錯」，所以 J／K 最多只能切換一次。

**連段是一張表，不是一棵樹。** 每個型態只有六個動作：第幾段 × 哪個鍵（J1 K1 J2 K2 J3 K3）。「只能換一次」這條規則原本看起來需要知道整條路線，但只要把「換過鍵的第二段」複製一份（J2s、K2s，資料相同、名字不同，`defmove-copy`），它的後續只允許新的鍵，規則就完全寫在資料裡；kit 用一個 `:grid` 鍵展開成十條連線。按鍵用「鎖存」：這一段期間按的 J／K 立刻從緩衝拿走、記最後一個允許的，等到這一段碰到對手才出；換過鍵之後再按原來的鍵，直接吃掉，也不會蓋掉已經記住的那一下，所以 J K J 會停在第二段。接觸閘門只改了一行：`chain-open-p` 要求有接觸，揮空就永遠不接。所有第二、三段的 K 都從揮刀中途進場（`:enter`），實際起手固定 14 格，所以不管前一段是 J 還是 K 都能連上。這些都在主機測試裡對每個型態、每條能走到的連線逐一檢查。

**O 收尾只接在打中的第三段之後。** 原本 O 可以取消任何打中的招式（單一 J、SP、Breaker），現在只有第三段（`:ender`）打中才開放，而且跳過衝刺前的氣勢，所以一定連得上。中立的 O 衝刺保留。攻勢 KŌSEI 則是在 `apply-hit` 裡加一行：自己的近戰判定碰到對手就給靈壓和瞬步，倍率 = 1 + 2 ×（1 − 自己的防禦量表%）。飛行道具、場地傷害、被招架的都不給。

**設計預測會變短，實際也變短了。** 照設計的數值跑種子測試，中位數 YY 106.8、YK 119.0、KK 121.7 秒，全部低於 125 秒的下限（KK 少了將近 50 秒）。拆開來看，打中次數每分鐘從 30 次變成 38 次，劍八的 KKK 很痛；更意外的是 SP2 衝刺的亂斬傷害翻了一倍多：以前連段的收尾是擊飛或擊退，接 SP2 會打空，現在第三段是踉蹌、跪倒，SP2 一定連得上，而電腦的「取消成 SP2」原本每一格都按，等於百分之百。和上次一樣加了執行期旋鈕（24000～29000），一次開六個無頭瀏覽器跑五輪：第二、三段的 K 傷害降到 80%、電腦連段選 K 的機率 0.5 → 0.3、不是紅血時接 O 收尾 0.35 → 0.15、SP2 取消改成打中當下擲一次、機率 0.3。結果 YY 129.4、YK 137.3（山本 10／劍八 10）、KK 130.4 秒，60 場全部 K.O.。KŌSEI 減半或關掉、電腦防禦追擊的機率調高，都落在雜訊範圍裡。

**寫了也不會發生的反射。** 設計裡「J 勝 K」的電腦反射，是看到對手的 K 還沒出手就用 J 插進去；可是 NORMAL 的感知延遲是 14 格，比任何 K 剩下的起手都長，按字面做永遠不會觸發。改成跟「擋下收尾後反擊」一樣，被擋的連段一結束就「感覺得到」下一段是 K，連按著防禦撐連段的時候也會檢查。即使這樣，電腦之間六十場也只出現 7 次，因為電腦在對手防禦時很少接 K。另一個設計上的小誤差：「被擋時的空隙 = 下一段的起手 + 被擋優勢」只在 −2 時成立，−3 的 K 之後其實多兩格，所以劍八和 KATATE 的 K2 → J3 被擋時，空隙剛好等於自己 J1 的起手，會互砍而不是被插。

**動畫。** 新畫了五個片段：山本始解的袖火（揮動燃燒的空袖子，火是畫面上的效果）、卍解東的落日（刀舉直、停住、垂直落下，地上留餘燼）、劍八的喧嘩踢、兩手型態的小手和諸手突刺，其他動作沿用舊片段換速度。順手修掉一個舊問題：美術檢視器的腳本沒把 `defrun` 定義的跑步片段算進去，`KE-R-STANCE` 之後每一張片段截圖的檔名都錯位了。

**還沒解決的。** 都還沒有真人試玩過：手機上三下點／上撥的節奏、O 晶片按住接毀魂技（LIGHT 鎖定還沒做）、KŌSEI 標籤在直式畫面的位置。第二、三段 K 打八折是為了電腦對戰的節奏，真人對戰可能不需要。

## 18. 手機直拿的畫面與鏡頭（2026-09-27）

使用者的要求：「再來請你調整手機模式的 UI 與運鏡。」這是 [DUEL_MOBILE_DESIGN.md](DUEL_MOBILE_DESIGN.md) 的 P2。做到一半使用者又給了兩個方向：「血條跟各種計量表 UI 我認為可以依據人物分開放上面與下面，如此就能放大 UI 使其不至於太小」，以及「角色可以再放大然後往畫面中下方移動，就算被大拇指擋到人物下半身也沒關係」。這兩條取代了設計裡原本「上方一整排面板、自己的量表貼在按鈕上」和「FOV 66°、畫面上移 0.22」的做法，細節在設計文件 §14。

**先看截圖再動手。** P0 的直拿畫面是把電腦版的 HUD 硬塞進兩個 0.36 倍寬的欄位：九朵魂火擠成一排撞在一起、連段數字蓋在計時器上、中間的標籤小於 11 CSS px 的文字下限；「HOLD O KIKON」這類提示和招式名稱在畫面邊緣被切掉；背後鏡頭讓上半部空著、兩個角色都在按鈕底下；過場動畫的構圖是給 16:9 的，直拿只看得到主角的一條邊。

**鏡頭：只改畫面端。** 引擎的相機多了一個 `shift-y`（鏡頭平移，設計裡的 G6），只有不是 0 的時候才寫進投影矩陣，所以電腦版每一幀的矩陣和以前是同一組浮點數。遊戲端新增一個直拿專用的背後鏡頭：站在 P1 後方 5.4 公尺、2 公尺高、偏右 0.5 公尺；鏡頭環繞的角度可以比模擬端的 `*behind-yaw*` 最多提前 20° 朝向對手（Hoho 或側步之後的「追上」），模擬端的值和轉速一個都沒動，所以將來連線時搖桿方向的換算不會不同步。瞄準點取兩個人的中間（左右看兩人的中心、上下看 P1 的腳和 P2 頭頂），鏡頭平移把它放在上下兩塊量表之間的中央。視野平常是 30°（框內），兩人拉開、靠牆（鏡頭被牆往內推）或對手跑到旁邊時才自動拉廣，最寬 100°。一開始照設計算的「框在按鈕上方」讓角色只佔畫面的四分之一；使用者說可以更大、擋到腳沒關係之後，框的下緣改到 0.82 倍高，角色在 2.2 公尺時 P1 約佔 0.49 的高度、P2 約 0.41（P0 大約 0.42／0.37，而且 P1 被切掉一邊）。

**過場動畫往後退。** 直拿時每個鏡頭的視野至少 66°，鏡頭沿著視線往後退，讓畫面的寬度裝得下橫向畫面中央那個正方形的內容（最多退 2.4 倍，不超出場地的牆）；鏡頭的左右偏移減半，主角不會被推到邊緣。直書的標題最大 0.36 倍寬。

**量表：依角色分上下。** 對手在最上方、自己在最下方（Home 條上面），各佔整個寬度：名字、攻勢倍率、一個標籤（和 P2 的計時器）；血條；防禦量表；魂火和四個沒有字的小量表（靈壓、瞬步、覺醒、角色量表或冷卻，顏色和電腦版一樣）。文字全部不小於 11 CSS px。瀏海和 Home 條的留白由頁面量 `env(safe-area-inset-*)` 告訴遊戲（`pwa.js` 的 get 3／4）。選單也重排了：模式選單往下移、選角和結算改成上下排列、手勢說明卡拉開行距。

**怎麼確認。** 除錯指令 2700 每 30 幀檢查一次兩個角色的上半身有沒有被量表擋住、有沒有至少七成在畫面內，並記下畫出來最小的字（引擎的 `*ui-text-min*`）；`tests/mobile-probe.py` 在四種手機尺寸加一次 iPhone 留白各跑一場 45 秒的電腦對戰和五個特定站位（1 公尺、2.2 公尺、24 公尺靠牆、對手閃到側面後 0.1 秒與 0.5 秒）。電腦版：41 張對戰截圖和上一個 commit 的建置逐位元相同，RAVEN（G1）、三場電腦對戰的雜湊（G2）、凍結截圖、smoke 都通過；觸控腳本跑兩次雜湊和戰鬥紀錄一致。

**還要在真機上看的。** 腳會站在按鈕之間（使用者同意）；P2 的招式名直書欄在右邊，可能疊到按鈕那一欄；過場動畫往後退之後人物比較小，要在手機上看是不是太小；計時器和標籤的大小是在 390 × 844 上調的。

### 18.1 手勢重新對應、量表分列、過場特寫（2026-09-28）

使用者的三個要求：「手勢模式［右手模式］幫我調整為朝上方滑動判別為向前衝刺，然後點擊區域改成分上下區塊來分開輕重攻擊」、「狀態列將魂魄改成獨立的一列，然後加粗血量與防禦外的量表」、「卍解跟毀魂技拍攝自身角色特寫時，可以不用全身入鏡」。細節和完整的手勢表在設計文件 §15。

## 19. Soul Break 新規則與劍八卍解（2026-09-28）

使用者在看完研究報告（`reports/血戰篇四角色格鬥設計研究.md`）之後做了兩批決定。2026-09-27：HP 扣到 0 的 Soul Break 要自動播放**攻擊方當下型態**的毀魂技動畫，扣的魂魄比主動毀魂多 1，而且只有 Soul Break 的單次上限從 4 放寬到 5（劍八三杯的 Soul Break = 5）；劍八可以打破「一場一次覺醒」，從三杯紅血按 P 開卍解，「腕」4 格，用完變片腕。2026-09-28 看完卍解的設計文件之後又加了兩條：**開卍解時劍八自己的魂魄直接變成 1**、**HP 回滿**；其餘四題（卍解的 L 現在就是咬、八千流用小小的黑白剪影、片腕維持鬼的樣子、電腦只在收尾時開）都照建議值。設計、使用者的決定、實作偏離與量測都在 [DUEL_KEN_BANKAI.md](DUEL_KEN_BANKAI.md)。

**Soul Break 只動了兩個地方。** `kikon-result` 多一個「Soul Break 用 `*soul-break-max-event*` 5、Kikon 用 4」的上限；要播哪一段過場寫成一個純函式 `kit-kikon-cine`（該型態 O 招的 `:cine`），主機測試直接檢查八個型態各自對到哪一段。結算順序照舊：同一步裡先看有沒有 Kikon，沒有才輪到第一個 Soul Break 的攻擊方。電腦對電腦很少打出 Soul Break，種子測試的中位數只因為過場變長而多了 1～2 秒（YY 129.4 → 131.8、YK 137.3 → 138.0、KK 130.4 → 131.5 秒），不必重調。

**卍解幾乎全是資料。** 能不能開寫在 kit 裡：只有三杯有 `:bankai-form :bankai`，卍解和片腕都沒有，所以一場只會有一次，不需要旗標。「腕」直接放在原本 NOME 的 kit 量表（`gauges-meter`），裂開的倒數用 NOME 的閒置計數；扣格、裂開、爆裂的時機是三個純函式（`pip-spend`、`pip-step`、`burst-due-p`）。爆裂要等「扣掉最後一格的那一招」打完才發生，這一點設計文件的自我批判就指出過：如果寫成「等他自由了才爆」，一直按 J 的玩家永遠不會自由。卍解的新身體是 `body-variant`：同一副骨架和受擊圓柱，換一組調色盤（壓低彩度的紅膚、白色的瞳孔：為此把基本型的瞳孔從 `:eye` 拆出自己的 `:pupil`，基本型畫出來一模一樣），再加上角、四道手臂裂痕和片腕的撕裂傷。裂痕一格一格出現要改「隱藏哪些部件」，但 `draw-body` 的 `:hide` 會蓋掉表情的隱藏清單，所以換成每種部件組合預先算好三個表情的清單，畫的時候只查表，每幀 0 B。

**自損加倍。** 設計原本是「紅血狀態下每格自損 30、爆裂 60」，但使用者改成開卍解時 HP 回滿，四格加爆裂只花 1300 裡的 180，等於沒有代價。改成 60／120 之後，用設計裡的「必開 vs 不開」測試量：60 個種子、電腦照進入規則一定開（p 1），YK 劍八勝場 28 對 27、KK 26 對 28，都在 ±9 的雜訊內；30／60 時 YK 是 32 對 27，偏向升級。**完全不看條件、能開就開**的話，YK 只剩 19 勝（同樣 33 個種子不開有 14 勝、開了只有 6 勝）：帶著一堆魂魄開卍解幾乎是自殺，這正是使用者要電腦「先看自己剩幾個魂魄」的原因。電腦的規則因此是：自己的魂魄不多於對手下一次 Soul Break 會拿走的量（開了也沒損失），或者對手已經快死（靈子 ≤ 60 % 或魂魄 ≤ 4）而自己只剩 ≤ 4 個魂魄，每次待在三杯擲一次 0.6。`:own-konpaku` 原本是 5，改成 4 之後前 20 個種子的 YK 劍八勝場從 13 變 12，回到 8～12 的目標裡。最後的種子測試：YY 131.8、YK 138.4（山本 8／劍八 12）、KK 131.5 秒，60 場全部 K.O.。

**寫了也沒有用的反射。** 設計要電腦看到「咬」的預備動作就閃開，但咬只有 10 格起手，比 NORMAL 的感知延遲 14 格還短，照南方束縛那樣按時機反應永遠來不及。實際做的是：看到一個 `:grab` 招式時不防禦、改成側步（反正防禦擋不住）。

**過場。** 卍解 186 格：跪地、草鹿森林（白卡、墨色樹幹、花瓣、八千流只出現兩張畫的小剪影、失真的雙重呼喚音）、紅色靈壓柱爆開、臉部特寫（角、無瞳的白眼）、「卍解」字卡、背後遠景。森林是在 UI 層畫的，所以把劍八放在畫面左三分之一、樹幹放兩側。毀魂技「真っ二つ」沿用天空斬的節奏，只換成鬼的顏色；它原本那條光就已經是垂直穿過畫面的，所以改成正面對著受害者拍，讓光剛好劈開他。第一版的跪地鏡頭是站著的：`hold-both` 凍住的是上一幀畫出來的姿勢，而換片段是在這一步才發生，所以第一拍只凍結對手。

**還沒解決的。** 片腕右臂每 20 格滴一滴血的效果沒做；都還沒有真人試玩過（P 的時機、咬的距離、「腕」在手機直式畫面上的大小）。電腦之間 20 場只開了 9 次卍解，而且大多開在已經輸定的局面，所以種子測試裡卍解一方 0 勝；這不代表卍解太弱，60 場的 A/B 才是判斷依據。

## 20. 連段追身、毀魂技的鏡頭、野性的鬼與「剩四魂」卍解（2026-09-28）

使用者這一批給了四個決定。一、「只要普通攻擊擦到，攻擊方在接續的攻擊動畫中就會靠近對手以保證後續的攻擊動作都能被打出來（這邊只講動作，不代表打出來就會造成傷害，還是能被防禦住）」。二、「劍八覺醒的毀魂技在準備揮刀的動畫看不到自己」，後來補充「無論常態還是始解卍解，在手持模式都有類似的運鏡問題」。三、劍八卍解的姿勢和動作要更野性。四、「劍八的卍解條件從紅血改成在剩餘四魂以下」。

**連段的閘門只剩第一段。** 以前每一段都要自己碰到對手，下一段才會出來（DUEL_STRINGS §2.2 的 contact gate）。現在只看第一段：這一串裡只要有一段碰到過對手，之後按下的每一段都會出來，就算中間某一段揮空也一樣。做法很小：latch 啟動的那一段在 fighter 上記一個 `chained`，`chain-open-p` 把它當成「被擋」的時機（恢復的最後 3 格）。因為只有「前面已經碰到過」才可能被 latch 接出來，所以一個布林值就夠，不必另外記「這串碰過沒」。

**追身。** 接續那一段的出招前搖裡，每一格照剩下的格數算速度，讓他在判定出現的那一格剛好停在招式距離內 0.4 公尺（`string-chase-speed`，最快 18 m/s，不會比 1.3 公尺更近，轉身至少每秒 360°）。每一格最多走完剩下的距離，所以不會穿過或衝過頭。它只是位移：防禦照樣擋得下，閃步、Hoho、倒地的無敵幀照樣躲得掉。電腦的連段本來就只在「這一段碰到了」才按下一段，所以 `ai.lisp` 不用改。種子測試（20 × 三組）：只有追身時 YY 134.7／YK 128.6／KK 136.1 秒，全部 K.O.，在 125～210 秒的窗口裡，沒有重調。

**鏡頭的根本原因。** 過場的 `shot-on` 瞄準的是腳本寫好的一個點（`:off`、`:ahead`，照 16:9 構圖），可是劍八的跳斬、衝刺、揮刀動畫會把身體帶離腳底最多 1.4 公尺；直拿的特寫又保留腳本的窄鏡頭（使用者之前決定特寫可以切到身體），4 公尺外畫面只有 0.8 公尺寬，所以他整個人跑出畫面。不是一個一個鏡頭去改，而是讓 `shot-on` 記下它拍的是誰（`*cine-subject*`），`camera.lisp` 的 `%keep-subject` 在直拿的鏡頭調整之後，把鏡頭左右平移，讓他擺好姿勢的骨盆留在畫面半寬的 55%（橫拿）／30%（直拿）以內；本來就在裡面就一動也不動，所以已經定案的構圖不變。這是畫面端的，模擬不讀鏡頭。查過山本的六段過場：他的鏡頭本來就都拍得到。

**野性的鬼。** 站姿改成很深的前傾蹲姿：腿彎而張開、背拱起、頭壓低往前伸、眼睛往上看、左手是鬆開的爪、斷刀拖在身後刀尖朝地，待機時背部起伏。走路、橫移、跑步、防禦都換成鬼自己的版本；共用片段的替換寫在身體變體的 `:clips` 對照表裡（`play-clip` 查 `body-clips`），所以片腕（還是鬼的身體）也一起換，而通用檔案仍然不帶角色名字。走路和跑步沒有重畫，是把共用的腿部關鍵格用 `oni-keys` 整體壓低、加彎。拳、咬、真っ二つ的跳躍和過場裡的起手、卍解登場的咆哮都重畫了。全部只動畫面：招式的 S／A／R、距離、判定一格都沒變，種子測試和 G2 不受影響。刀的角度是試出來的：手腕 −150° 時刀是往後上翹的，−100° 才是拖在地上。

**卍解改成剩四魂以下。** `bankai-allowed-p` 從 `(free red)` 改成 `(free konpaku)`，門檻 `*bankai-konpaku*` 4；HUD 的 P BANKAI 提示、手機的 AWAKEN 鈕都走 `bankai-ready-p`，一起跟著變。電腦的進入規則照舊（沒什麼好輸的，或對手快輸了），只是不必先變紅。結果卍解開得多很多：YK 20 場開了 14 次（開的一方贏 7 場），KK 19 次（贏 6 場）；之前紅血時是 3 次和 6 次，一場都沒贏。種子測試最後 YY 134.7／YK 137.1／KK 125.8 秒，KK 貼著下限。

**G2 參考值。** 三組的 hash 行都變了：YK 的種子 7 現在是 `winner P2 konpaku 0-1 ticks 7365 secs 122.8`，已經更新 `tests/style-cvc-ref.txt`、DUEL_GAMEPLAY、`duel.py` 的註解和教學 9.5。

**還沒解決的。** 追身、野性的姿勢、剩四魂的卍解都還沒有真人玩過；KK 的中位數離下限只有 0.8 秒，下一次改動如果讓它更短，第一個要調的是電腦的卍解機率 `:p`（debug 37000+k）或追身速度 `*chase-max*`。

## 21. 練習模式、設定，以及把單手併進 VS CPU（2026-09-28）

使用者的要求：「請幫我添加『練習模式』與『設定』（調整手持模式與其開關等等）後將『one hand vs cpu』與『vs cpu』整合」。細節都是先幫使用者選好的預設值，寫在 [DUEL_GAMEPLAY.md](DUEL_GAMEPLAY.md)（Flow、SETTINGS、PRACTICE 三段）和 [DUEL_MOBILE_DESIGN.md](DUEL_MOBILE_DESIGN.md) §16，使用者可以再改。

**選單。** MODE 變成 VS CPU／PRACTICE／VS PLAYER／CPU VS CPU／SETTINGS／CONTROLS，每台裝置都一樣，游標一開始就在 VS CPU。原本的「ONE-HAND VS CPU」和「HAND」兩列拿掉了；要不要單手改由設定 ONE-HAND（AUTO／ON／OFF）決定。AUTO 的規則就是舊的「觸控裝置直拿時預選 ONE-HAND VS CPU」，所以手機上的使用者體驗不變：點 VS CPU 就是單手。這條規則寫成純函式 `one-hand-on-p`（`control.lisp`），主機測試把 3 個選項 × 觸控與否 × 直橫 12 種情況都列出來檢查。

**設定是資料。** `*settings*` 一列一筆：代號、標籤、選項、預設、選項代表的數值、說明。畫面（`hud-settings`）、切換（`settings-step`）、生效（`apply-settings`：手的方向、辨識器的 `tap-split` 和 `flick-min`、鏡頭）和存檔都只讀這張表。頁面那一邊（`pwa.js`）只多了「第 10＋i 號服務＝第 i 列」，存成 `localStorage` 的 `soulduel.<名稱>`，值是選項編號＋1，所以 0 永遠代表「沒存過／存不了」，Lisp 就退回預設值。HAND 沿用原本的 `soulduel.hand`，舊的存檔照樣有效。音量沒有做：引擎只開放了音樂的音量，沒有總音量或音效音量，照「引擎有才做」的原則跳過。

**鏡頭設定的一個陷阱。** 舊的單手入口會呼叫 `(set-cam-behind t)`，也就是直接把 CAMERA 選項改成 BEHIND。變成「存起來的設定」之後這樣做會悄悄覆寫使用者的選擇（手機上打一場單手，回到電腦就發現 SIDE 變成 BEHIND）。改成 `set-cam-behind` 在單手時自己把「用背後視角操作」打開，設定值本身不動。

**練習模式幾乎全是重用。** 假人就是 P2 的電腦大腦：STAND／GUARD ALL／GUARD AFTER HIT 時把大腦關掉，讓它「按住」防禦（跟 debug 2330+k 的 O 模組測試用的是同一招），CPU 時打開，難度就是選角時選的。什麼時候按住防禦是純函式 `dummy-guard-left`，GUARD AFTER HIT 是「被打中或擋下的那一刻起，到自由之後 60 格」，這樣一串連段的第一下會中，接不上的後段就會被擋，能拿來確認連段是不是真連。沒有計時：`match-system` 在練習模式改呼叫 `practice-step`，每一格把假人的魂魄補滿、連段結束就補血（HP REFILL AUTO）、GAUGES INFINITE 時把自己的量表補滿。K.O. 只可能發生在自己身上（例如劍八卍解後只剩 1 個魂魄），`match-over` 在練習模式改成重來一回合並把雙方補滿。連段計數直接沿用原本的，只是練習時不會淡出、單下也算。

**一個取捨。** 角色量表（山本的 Inferno、劍八的 NOME）不補，讓 Hellfire 和三杯照原本的節奏出現，不然山本會永遠卡在 Hellfire。第一版還讓劍八在三杯時的血停在剛好紅血（當時卍解要「三杯＋紅血」）；同一天使用者把卍解條件改成「三杯而且自己的魂魄 ≤ 4」（由另一批工作實作），這個特例就拿掉了，改用下面的魂魄設定來試。

**血量和魂魄數（使用者追加：「練習模式增加血量跟魂魄數的調整功能」）。** 暫停選單多了 P1 HP、P1 KONPAKU、DUMMY HP、DUMMY KONPAKU 四列（血 100／75／50／25／10%，魂魄 1～9，預設都是滿的，所以原本的行為不變）。改了立刻生效，而且它們取代了原本的「全滿」：重置位置、補血、K.O. 後的重來、INFINITE 都回到這四個值。清單變成 12 列，直拿時會壓到 P1 的量表，所以 `hud-menu` 多了一個「最低到哪裡」的參數：列數多到放不下時列距和字一起縮，原本放得下的選單一個像素都沒變。

**紅色的魂火（使用者追加：「將目前放出毀魂技可以削減的魂魄數量標記為紅色」）。** 每一邊的魂火，最後 N 顆畫成血紅色，N 是對手「現在」放 Kikon 會削掉的數量。這個數字不另外建表，直接用結算的同一條規則：`kikon-result`（上限與剩下的數量）配上對手目前型態的 `:kikon-konpaku`，所以之後新增的角色（露琪亞）不用改 HUD。原本「自己紅血時所有魂火一起變紅」的效果被取代：現在紅的只有會被削掉的那幾顆，紅血時它們會閃。HP 歸零的 Soul Break 還會多 1 顆，這裡沒有顯示。

**J J J 在第一版腳本裡打不出第三段的原因。** 不是連段程式的問題。同一個腳本用 `--fixed-dt` 跑，J1、J2、J3 都出來了；即時模式下這台機器同時跑著十幾個無頭 Chrome，按鍵照牆上時間送進去，模擬的步數卻是一幀補好幾步，第三下的按鍵落在 J1 還沒結束的時候，被鎖存在同一格（連段的鎖存只記一個「下一段」，後按的覆蓋先按的），於是只出了 J2。擋下時更明顯：被擋時下一段要等恢復的最後幾格才接，第三下同樣落在 J1 裡。所以練習腳本改用 `--fixed-dt` 跑。

**測試。** `duel-control-test` 53 → 71 項（含血量、魂魄的設定值和紅色魂火的數量）；新腳本 `duel-practice.json` 用鍵盤走一遍設定和練習模式（紀錄 `duel setting …`、`duel practice …`）；`duel-flow.json` 的 VS PLAYER 往下多按一次；`duel-touch-left.json` 改從 SETTINGS 換左手；`duel-touch.json` 不用改（VS CPU 剛好在原本 ONE-HAND VS CPU 的位置），前後兩版在 `--fixed-dt` 下的雜湊與戰鬥紀錄一致。對戰規則沒動，所以 CPU 對 CPU 的決定性參考值（`tests/style-cvc-ref.txt`）不變。

## 22. 第三個角色：朽木露琪亞與「絕對零度」（2026-09-28）

## 23. 露琪亞的頭放大、L 量表只畫一格（2026-09-28）

## 24. 露琪亞的冷度量表、劍八一套連段一格、南不再冷卻、冰色線條與半透明的靈壓（2026-09-28）

同一天試玩後的決定和一個錯誤回報一起做，一次跑平衡：露琪亞覺醒後改成一條冷度量表（設計在 scratchpad 的 `design-rukia-temp.md`，使用者的決定寫在 [DUEL_RUKIA.md](DUEL_RUKIA.md) 最後）；劍八卍解的 J／K 連段「打完一套才扣一格腕」（[DUEL_KEN_BANKAI.md](DUEL_KEN_BANKAI.md) 最後）；山本卍解的「南」不需要冷卻（[DUEL_YAMA_REWORK.md](DUEL_YAMA_REWORK.md) 最後）；露琪亞白色樣子的眉毛和人物邊線改成冰藍色；劍八的黃色靈壓改成半透明。

**冷度量表。** 原本的溫度階梯（防禦 40 幀降一階、計時器、THAW／CRACK 兩個型態、L 冷卻）全部拿掉，換成一條冷度 0～200、畫成兩條疊在一起的量表（使用者的話：第 1 條滿 → −50°，第 1 條回到空 → −18°；第 2 條滿 → −273°，第 2 條回到空 → −50°）。防禦每秒冷 90（一條 1.1 秒，從 −18 到 −273 2.2 秒：設計原本是 3.3 秒，使用者後來說「加快露琪亞降溫的速度」），沒防禦就回溫：−18 每秒 10、−50 每秒 12、−273 每秒 5。−273 本來設計成回溫最快（2.9 秒就退回 −50），使用者後來說「請將 -273° 的回溫速度放緩，使維持在 -273° 的難度減少」，所以改成三帶裡最慢的，上面那條要 20 秒才會自己用完。被擋下的近戰讓她更冷（防禦值 ×1.5），真的被打中讓她回溫（傷害 ×0.2）。出招花冷度：−18 只有 L（25，不夠就不能出，這是使用者的決定），−50 和 −273 每一招都要花；−273 的 L 和兩個 SP 一次花掉整條上面的量表，所以放完一定退回 −50。冷度在哪一帶就是哪個型態，換型態只在她空著的時候發生（純函式 `temp-band`），所以一套連段會用開始時那一帶的版本打完。

**越冷越強。** 每一帶的招式距離 ×1.0／1.1／1.35、霜 30／60／90 幀、L 從霜柱（半徑 2.5）長成氷震（3.5）再長成零度凍結（5.5，凍住 45 幀），SP1、SP2、O 也一帶比一帶長、痛。動作也不同：−50 換上結霜的刀（`:ru-rime`）和四個改關鍵影格的新片段（雙手迴旋、掌與刀一起推、雙掌下壓、雙手插刀），−273 換成冰刀，J2 變成手掌反拍、K1 是 4.3 公尺的冰刺。越冷也越慢（走 3.4／2.8／不能動），但身邊多了「寒域」：對手在半徑 3／4／5.5 公尺內往外退的那部分速度打 0.85／0.7／0.55 折，往後閃步變短，往旁邊閃不受影響（`field-velocity`、`field-step`，只有對手是露琪亞的時候才算，所以山本和劍八之間的對戰一個位元都不變）。−273 按住 U 是「撐住」：不回溫，但防禦量表每秒掉 8，掉光就碎裂。碎裂現在是一個事件，不是型態：冷度歸零、自損 60、跪 30 幀，接下來 2 秒防禦不會降溫（量表變灰、寫 THAW）。

**HUD。** 她覺醒後的 L 沒有冷卻，所以不畫 COOLDOWN 那一列，冷度量表自己一列，試玩時「溫度字蓋到 COOLDOWN 字、溫度條蓋住 L 條」就不會再發生。量表是兩條疊在一起：第一條淺藍、第二條白色蓋在上面，左端三個小方塊亮幾個就是第幾帶，L 會花掉的那一段變暗（不夠時只剩一條白線），−273 閃動，碎裂時劃過一條血紅的細線。直拿時是同一條縮小版；單手模式拇指圈外的白弧就是冷度 / 200。

**平衡。** 第一次照設計的倍率做（−18 沿用 1.32），A/B（60 個種子，P1 一定覺醒 vs 絕不覺醒）覺醒在 RY 多贏 11 場、RK 多贏 9 場，是升級不是增減項；改成設計的 1.20／1.35／1.55 之後，「越冷每秒傷害越高」這道關卡在 RK 反過來了（−18 19.6、−50 17.5），因為 −50 的電腦一直在防禦冷卻。最後是 −18 1.15、−50 1.5、−273 1.65，−50 的電腦防禦 0.55 → 0.45、氷震權重 2 → 3，−273 的電腦在 7.5～14 公尺放白漣。之後使用者又做了兩個決定：−273 回溫變成最慢（每秒 5），以及「加快露琪亞降溫的速度」（防禦每秒 60 → 90、擋下近戰 ×1.0 → ×1.5）。降溫變快以後 A/B 三組都沒有「不覺醒」比較好（0／+1／+3），所以照使用者給的方向調 −273 的出招花費：J／K／O 從 15／30／50 提高到 20／40／60，電腦「撐住」的機率 0.35 → 0.2。最後的節奏關卡（debug 2113，每組 20 場，全部 K.O.）：YY 134.7、YK 136.2、KK 131.2、RY 135.6（露琪亞 11 勝）、RK 148.1（13 勝）、RR 183.1 秒；A/B RY 30／28、RK 35／32、RR 26／27（差距都在 3 以內，RR 是「不覺醒」贏）；每秒傷害 −18／−50／−273：對劍八 19.1／27.0／55.5、對露琪亞 14.7／25.1／34.2、對山本 24.9／34.6／51.1，每一組都是越冷越高。RK 的 20 場裡 −273 出現 35 次（19 場至少一次），佔覺醒時間的 6%；其中 16 次以碎裂結束（46%，60 個種子的樣本是 29%）。回溫變慢之後「撐住」幾乎沒有用處（每秒省 5 點冷度卻要付 8 點防禦量表），先保留。

**劍八：一套連段一格。** 使用者說「更木劍八卍解的 K 改成打完一套才扣腕」。原本每個 K 出手就扣一格，KKK 加 O 收尾就把四格用光。現在一整套（K、KK、KKK、KJJ、JKK……加上 O 收尾）只扣一格，在這套結束時才扣（打完、被打斷或揮空都算），同樣自損和裂痕閃光；JJJ 還是不扣。實作是量表上多一個「這套還欠一格」的旗標（`gauges-arm-owed`），K 起手、K 連段和 O 收尾只設旗標，`arm-step` 在他不在連段或收尾裡的第一幀結帳（純函式 `string-pip-due-p`，主機上測）。K 仍然要有一格才能出；欠著一格時想用 SP／L 取消要再多一格，O 收尾不用。L、SP1、SP2、I、一般的 O 還是每次一格。KK 的中位數從 125.8 變成 131.2 秒。

**劍八：最後一格腕放不出來。** 使用者回報「劍八卍解後『腕』歸零的瞬間就會打斷當前的出招，導致最後一腕其實放不出來」。用 debug 2388（卍解只剩一格）逐一試：L、SP1、I、一般的 O 都會完整打完再爆裂，但 SP2 不會：SP2 衝撞打中後由掛鉤接出另一招「殴り飛ばし」（`:land` 接招），爆裂的判斷只認得「花掉最後一格的那一招」，看到另一招就當成「之後的新招式」立刻爆裂。改成一套連段扣一格以前，K 連段也一樣：K2 花掉最後一格，接著的 K3 會被切掉。修在唯一共用的地方（`arm-step`）：等待中的爆裂會「跟著招式鏈走」，正在出的招如果是它的延續（任何按鍵的連段下一招、`:land` 接招、第三段之後的 O 收尾，`move-follows-p`），就改成等這一招，整串打完才爆裂；自己另外出的新招（咬完之後的 J1）照樣會被切掉。一套連段結帳時如果他正用 SP／L 取消，也是等那一招打完。主機測試加了這條鏈的判斷和 L、SP1、SP2、K 連段加 O 收尾各自「完整打完才爆裂」的幀數。

**山本：南沒有冷卻。** 使用者說「山本的『南』本身就是消耗靈力計量表使出的 SP2，不需要有冷卻」。拿掉 600 幀冷卻以後，整個遊戲沒有其他 Shift+L 有冷卻，所以 §23 加的那條 L 條下面的細線和它的第二個「被拒絕」閃光一起刪掉。電腦沒有依賴南的冷卻；有記錄的 YK 20 場裡南一共放了 8 次，沒有亂放，所以沒加電腦的限制。G2：YY（種子 7）結果一樣是 `winner P1 konpaku 2-0 ticks 9248 secs 154.1`，只有 t=6600 那一行的冷卻欄位從 220 變成 0；YK、KK 完全不變（這兩場沒有卍解的連段）。

## 32. 千手丸：判定距離對上畫面（2026-09-29）

使用者玩了千手丸之後說：J／K 的判定距離比動畫顯示的長很多，很難判斷距離；要讓畫面上的動作和攻擊距離一致，怎麼改動畫、怎麼改判定由我決定。

**量法。** 判定體的「最遠邊」是對手受擊圓柱靠近她那一側最遠能站的位置（弧形就是半徑，膠囊就是終點加半徑，對手中心再多 0.36～0.45 公尺才碰不到）。畫面上打到的東西是針尖（弧形量水平半徑、膠囊量正前方），或 K 招的道具最遠端。回聲手臂只是跟著骨架的雙手、繞脊椎轉一個角度，不會比雙手更遠，所以不算。原本針只有 0.9 公尺（乘上體型 0.88），出招那幾幀針尖只到 1.5 公尺左右，J 的判定是 2.4／2.4／2.6；K1 的膠囊到 3.5、K2／K3 到 2.8，畫面上卻只有針和手；卍解還整組 ×1.15（說是「每隻手都帶著布」，但從來沒畫布）。

**J：先縮判定，結果被打爆，改成把針加長。** 第一次把 J 縮到針尖（1.6 公尺，再加長一點針變 2.0），節奏測試中位數都還在範圍內，但她幾乎不贏：SY 1～4 勝、SR 2 勝、SI 2 勝；把始解傷害倍率調到 2.0 也只讓 SY 變 5 勝、中位數卻掉到 127.9 秒。她是被距離壓制，不是傷害不夠。所以反過來：針從 0.9 公尺加長到 1.8 公尺，和她一樣高（刺絡本來就是一根巨大的縫針），出招姿勢再往前送 0.1 公尺左右，針尖到 2.35～2.37 公尺：J1／J2 維持 2.4，J3 從 2.6 縮到 2.4。卍解拿掉 ×1.15，J 和 K2 跟始解一樣。

**K：道具真的伸到判定邊。** 待ち針是兩手各一根長針直直刺出到 3.5 公尺；纏り是從針尖甩出兩股紅線，拱起來落在 2.8 公尺；絎け是五根針插進地面（2.1～2.8 公尺、±40°），線連回手上；反物打ち是一匹布從雙手攤出到 4.5 公尺；巻き取り是兩條布從手拉到他腳邊。出招前 4 幀甩出去、判定期間全伸、之後 8 幀收回。長針一開始有墨線外框，但細長縮放讓外框被拉成一條黑線超出針尖，所以針不加外框；絎け的針用實際尺寸的道具畫，保留外框。K 的判定都沒動。

**測試。** `duel-rules-test` 在千手丸那段之後載入 `anim.lisp`，從 `senjumaru-art.lisp` 讀出她的姿勢，對七個型態的每個 J／K 連段跑前向運動學，檢查判定幀的針尖（或道具最遠端）和判定最遠邊相差不超過 0.15 公尺（主機沒有 C，`anim.lisp` 用到的幾個浮點巨集在測試裡換成一般 CL）。故意把 J1 改回舊值時這一項會失敗。3559 項全過。

**星的吸取（同一天，使用者：「在第 6 綛『星』的範圍內，對手無論受擊還是攻擊都不應該回復量表，吸收的量表要反還到千手丸身上」）。** 他站在她已展開的星裡時，不管是被打、防禦、格擋還是自己的刀碰到人，都拿不到任何量表：靈壓、瞬步、鬥志、kit 量表（NOME、Inferno、冷度、鎖鏈和結界的回補、失去魂魄時的鬥志）全部沒有；本來會拿到的靈壓和瞬步改給她（各自到上限為止），其他的就沒了。星原本每秒吸 30 靈壓、15 瞬步，現在實際吸到多少就給她多少。通用檔案只多一個掛鉤：對手 kit 的 `:siphon`，`combat.lisp` 的 `siphon-of` 在每次增加量表時問一次，所以星一消失或他一走出去就立刻失效，不用另外清狀態。純函式 `hit-gains` 和 `gauge-move` 放在 `rules.lisp`，主機測試（3566 項）檢查拒絕、轉給她、鬥志不轉、吸取以實際數量並封頂。除錯 2480 是一個探針：星罩著兩人、兩邊靈壓都是 0，他打她兩下，她的靈壓 2 → 30 → 75，他的瞬步 16 → 0 流到她身上，他的靈壓不動。節奏測試（種子 1～20）和判定修正後逐場相同：SY 135.6、SK 142.7、SR 173.8、SS 187.2、SI 166.7 秒，100 場全部 K.O.。電腦之間很少排到星而且他又站在裡面，所以這 100 場裡一次都沒吸到；它有沒有作用要看 2480 的探針。
