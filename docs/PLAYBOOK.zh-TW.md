# 遊戲開發經驗手冊（PLAYBOOK）

這份手冊把 RAVEN EDGE 和 SOUL DUEL 兩款遊戲一路做下來的經驗整理成可以重複使用的做法，給「之後想用同一套方法做別的遊戲」的時候參考。它不是規格書：規格在各自的設計文件裡，理由和過程在 [DEVLOG.zh-TW.md](DEVLOG.zh-TW.md)。這裡只留下換一款遊戲也成立的東西，並註明出處，想看細節可以順著連結回去。

同一份經驗也做成了四個給 Claude 用的 skill，放在 repo 的 [`skills/`](../skills/)，並連結到 `~/.claude/skills/`，任何專案都能觸發：

| Skill | 什麼時候用 | 對應本手冊 |
|---|---|---|
| `lisp-wasm-game` | 在這套引擎上開新遊戲、加引擎功能、除錯建置或執行期問題 | 第 2 章 |
| `sim-balance-gates` | 改規則、數值、AI，要驗證平衡與節奏 | 第 3 章 |
| `procedural-ink-style` | 做模型、動作、特效、HUD、演出、音效，或畫面與判定對不上 | 第 4 章 |
| `game-dev-workflow` | 接到任何功能需求時的整體流程 | 第 5 章 |

每個 skill 資料夾裡的 `reference.md` 是英文的詳細筆記，每一條都標了出處（檔案路徑、文件章節、DEVLOG 節次），也標了「可以通用」還是「只屬於這個專案」。

---

## 1. 這個範例是什麼、什麼時候適合拿來用

**範例的組成**：用 Common Lisp 寫的網頁 3D 遊戲。Lisp 先由 ECL 編成 C，再由 Emscripten 編成 WebAssembly，畫面用 SDL3 的 SDL_GPU 走 WebGPU。整個 repo 沒有任何美術或音訊素材檔：模型、動作、特效、文字、音效和配樂全都是啟動時用程式產生的。

- `engine/`：引擎（package `ENGINE`），不知道任何遊戲。
- `game/`：第一款遊戲 RAVEN EDGE（忍外風格的動作遊戲，低面數霓虹雨夜）。
- `duel/`：第二款遊戲 SOUL DUEL（BLEACH 風格的 3D 格鬥，漫畫墨線風）。
- `examples/hello`：123 行的最小範本，新遊戲從它複製開始。

**適合**：

- 想做小型、程式生成內容的網頁 3D 遊戲，並且願意接受 Lisp 工具鏈的限制。
- 有「電腦對電腦」可以模擬的玩法（格鬥、動作、對戰），想用大量模擬來調平衡。
- 想要一個能長期迭代、每個決定都留下紀錄的專案。

**不適合**：

- 需要大量美術素材（貼圖、模型、配音）的遊戲。這套方法的優勢是零素材，硬塞素材反而失去它。
- 需要多執行緒或在 Lisp 裡等待非同步事件的遊戲。GC 的做法（第 2.3 節）在那種模型下不成立。

## 2. 引擎與工具鏈

詳細清單：[`skills/lisp-wasm-game/reference.md`](../skills/lisp-wasm-game/reference.md)。原始文件：[ARCHITECTURE.md](ARCHITECTURE.md)、[ENGINE_API.md](ENGINE_API.md)、[TUTORIAL.zh-TW.md](TUTORIAL.zh-TW.md)。

### 2.1 分層與新遊戲怎麼接上

- 引擎分成三種語言、各放各的檔案：Lisp API（`engine/lisp/`）、C（`engine/c/`，只有一個標頭檔宣告所有 Lisp 會呼叫的 C 函式）、WGSL 著色器（`engine/shaders/`）。
- 新遊戲就是一個資料夾加一個 `MANIFEST`：第一行 `# title: 名稱`，接著依相依順序列出原始檔。遊戲在載入時呼叫一次 `run-game`，交出 `:load`（可以分很多步）、`:start`、`:frame`、`:debug`、`:stats`。
- `./build.sh <資料夾>` 產生 `dist/<資料夾>/`。注意：不帶參數的 `./build.sh` 只會建 `game/`。
- 選用的 `<遊戲>/web/` 放網頁外殼片段、PWA 圖示、`manifest.webmanifest`、`sw.js`（建置時會自動寫入版本雜湊）。
- **「第二個使用者」規則**：一個功能只有在第二款遊戲也需要時才搬進引擎。SOUL DUEL 本身就是拿來檢查引擎缺口的：開工前先讓一個唯讀 agent 列出 20 個缺口，開發中又找到 15 個。做第三款遊戲時，預留一輪「引擎缺口盤點」。

### 2.2 建置、執行、除錯的日常

- 建置時間：hello 約 7 秒、RAVEN 約 12 秒、SOUL DUEL 約 43 秒。整個遊戲是一個編譯單元，改一行也會全部重編。
- 本機看：`python3 -m http.server -d dist/<遊戲> 8000`。要在別的裝置看，WebGPU 需要 HTTPS（localhost 例外）。
- 無頭執行：`node tools/run.mjs dist/<遊戲> --fixed-dt 16.666667 --secs 8 --shot s.png [--script steps.json]`。
  - `--fixed-dt` 讓同一個執行檔、同一份腳本拍出**逐位元相同**的截圖。
  - 遇到 JS 例外或 WebGPU 驗證錯誤會回傳 1，所以順便就是著色器的冒煙測試。
- 除錯指令：`Module._debug_cmd(n)` 是整數指令通道。場景、執行期調數值、凍結過場的某一格、種子對戰全都編成整數。每個遊戲先劃好自己的整數範圍，寫成一張表；SOUL DUEL 曾經發生過範圍撞號。
- 純規則測試：把規則寫成純 CL 檔，host 上的 ECL 一秒內就能載入測試，不用建置。
- `tools/pkgcheck.sh <遊戲>`：**每改一批就跑**。ECL 不會警告未定義的函式、沒匯出的引擎符號，也不會警告遊戲意外覆蓋了引擎函式。曾經有一個這樣的錯誤一路跑到使用者的手機上。

### 2.3 最貴的幾個坑

| 症狀 | 原因與規則 |
|---|---|
| 記憶體莫名損壞、物件消失 | Boehm GC 是保守式的，在 wasm 上看不到區域變數。規則：Lisp 執行時關掉 GC，只在幀與幀之間回收；絕對不要從 Lisp 呼叫 GC；C 的靜態變數如果存 Lisp 物件，要註冊成 root |
| 每幀配置量（consing）高、GC 卡頓 | ECL 的單精度浮點數在 let、結構欄位、全域變數、非 inline 的呼叫裡都會被裝箱。熱路徑用 `defun-fast`、`let*`、f32 陣列、`!` 結尾的寫入式函式、`f-min`／`f-max`；不要寫 `incf aref` |
| 啟動時記憶體尖峰 | 重的生成工作（模型、音效合成、外框殼）塞在同一步。拆成很多個 `:load` 步驟，中間會 GC |
| emcc 編一個檔要好幾分鐘 | 同一個函式裡有很多 `handler-case`／`unwind-protect`（每個都是 setjmp）。每幀只留一個例外處理，大函式拆小 |
| 執行後重新定義函式沒有效果 | ECL 編譯後是直接呼叫。要改就改原始碼再重建 |
| 沒有訊息的 `call_indirect` 當機 | 某個 C 編譯少了 `-DECL_C_COMPATIBLE_VARIADIC_DISPATCH` |
| 亂數每次都產生大整數 | wasm32 的 fixnum 只有 30 位元。亂數放在 C（`engine/c/rng.c`） |
| 罕見分支裡浮點數當機 | ECL 的 `pi` 是雙精度。用單精度常數 |
| WebGPU 錯誤、畫面全黑 | 不能呼叫任何會阻塞的 SDL_GPU 函式；拿不到 swapchain 就跳過這幀；WGSL 綁定名稱不要含 `sampler`／`read`／`write` |
| 原生版和 wasm 版結果慢慢分岔 | glibc 和 musl 的數學函式差最後一個位元，x87 浮點也不同。原生版用 `LD_PRELOAD` 載入同一份 musl，並加上 `-msse2 -mfpmath=sse -ffp-contract=off` |
| 使用者手上還是舊版 | 原生模擬或測試的建置不會更新 `dist/`。交付前最後一步一定是 `./build.sh <遊戲>`，並確認 `index.wasm` 比所有改過的原始檔新 |

### 2.4 預算

- 每幀配置量：幾十 KB 以內（RAVEN 戰鬥中約 20～41 KB，SOUL DUEL 約 12～17 KB）。常用的引擎繪圖呼叫都是 0 B。
- 啟動記憶體：兩款遊戲都約 57 MB，上限訂在 110 MB。
- 繪製次數上限 600（SOUL DUEL 實際 45），粒子上限 1200。
- 開工前先寫一張「估計 vs 實測」的預算表，做完再填實測值。

## 3. 模擬與平衡測試

詳細清單：[`skills/sim-balance-gates/reference.md`](../skills/sim-balance-gates/reference.md)。原始文件：[DUEL_GAMEPLAY.md](DUEL_GAMEPLAY.md)（gate 規則與指令）、[DUEL_AI_V2.md](DUEL_AI_V2.md)、[DUEL_LEARNING.md](DUEL_LEARNING.md)、[DUEL_ASSIST.md](DUEL_ASSIST.md)。

### 3.1 確定性：同一個種子要打出同一場比賽

這是一切平衡測試的地基，**要在寫內容之前就做好**，事後補非常痛：

- 固定 60 Hz 步進；慢動作用「跳過步驟」做，打擊停頓也是模擬時間。
- 兩條亂數：`sim-rnd01` 只在步進裡給規則和 AI 用，`rnd01` 給特效等外觀用，絕不混用。
- 輸入只在步進裡讀進虛擬手把（vpad）。鍵盤、觸控、CPU、測試腳本寫的都是同一個 vpad。
- 每場比賽開始時，把所有跨場的狀態一次重設。
- 每 600 步印一行量化過的狀態雜湊，比賽結束印一行結果。比對這些文字行，就是全部的確定性測試。

**真的發生過的破壞方式**：

- 慢動作累加器把殘值帶到下一場。
- 某角色的每側狀態寫了「每場重設」卻沒有重設。
- glibc 和 musl 的 `sinf` 差最後一個位元。
- 多擲一次骰子會讓後面所有決定全部重洗。所以機率為 0 的功能不能擲骰；量測用的計數器只計數、不擲骰；學習型 AI 用自己的亂數。

### 3.2 測試由快到慢分層

| 層 | 工具（範例） | 何時跑 |
|---|---|---|
| 純規則測試 | `tests/duel-rules-test.lisp` 等四組，host 上幾秒 | 每次改動 |
| 參考回歸（G2） | 三場固定種子的電腦對電腦，逐行比對 `tests/style-cvc-ref.txt` | 每次改動；刻意改變行為時重寫參考檔 |
| 種子節奏 gate | `tools/simgate.py`，原生模擬，15 組 × 20 局約 14 秒 | 改規則、AI、數值時 |
| 覺醒 A/B | 三條互不重疊的 60 局種子流 | 改到有覺醒的角色時 |
| 連打玩家 gate | `tools/assistgate.py`，用腳本模擬新手 | 改 AI 或輔助功能時 |
| 截圖、效能、冒煙 | `tests/style-gates.py`、`tools/run.mjs` | 改畫面或建置時 |

規則測試裡值得照抄的幾種斷言：

- **幀數重算**：每招實測的被擋有利幀要等於招式表。
- **組合走訪**：每條連段路線都走一遍。
- **幾何關係當不變量**：抓技範圍 < 所有輕攻擊範圍、觸發了的抓技一定打得到。
- **畫面對判定**：見第 4.3 節。

### 3.3 gate 的規則（SOUL DUEL 現行）

- 每場都要 K.O.；跨角色組合的中位數在 125～210 秒；同角色內戰可以超過 210 秒。
- 只動到一個角色的檔案，就只跑那個角色的組合和它的覺醒 A/B；動到共用規則就 15 組全跑。
- 20 局的中位數落在範圍外，就改跑 60 局，以 60 局的結果為準。
- 覺醒 A/B：不覺醒的一方在三條種子流上都要贏至少 20／60。這是使用者「覺醒偏強沒關係，只要不是強到無法贏就好」的數字化。
- 要歸因變化時，先在父 commit 上用同樣的 gate 跑一次基準。

### 3.4 gate 沒過怎麼辦

1. 先量測時間或勝場花在哪裡（加計數器、印 log，每個程序寫自己的 log 檔，不要共用）。
2. 先動設計裡事先列好的「槓桿」；試過但沒用的也記下數字。
3. 還是不行就**停下來回報使用者**，附上前後數字和兩三個選項，不要偷偷改別的數值補回來。
4. 使用者接受的話，把原話和日期寫進 gate 規則、設計文件、DEVLOG 和 commit。這次的例子是 YK 119.5 秒，使用者說「我接受這個節奏」。

**讀數字要帶著雜訊**：20 局約 ±2 勝；多一次擲骰重洗後約 ±5；60 局約 ±4。所以 A/B 用三條種子流，選數值看「所有條件都滿足」，而不是挑單一最好的數字。

### 3.5 CPU AI

- **結構**：CPU 跟人一樣按虛擬手把。每一步依序是：感知（有延遲的快照）→ 固定優先序的反射 → 中立時的意圖與距離帶選招。
- **難度**：主要靠感知延遲（EASY 24／NORMAL 14／HARD 8 格），再加每個難度的機率表，且 EASY ≤ NORMAL ≤ HARD。
- **反覆出現的坑**：
  - 反應比威脅慢的規則永遠不會觸發。要改用 CPU 自己立刻感覺得到的狀態來決定。
  - 機率要「每個事件擲一次」，每一步都擲就等於必然發生。
  - CPU 自己移動用真實距離，判斷對手意圖用感知距離。
  - 按住的按鍵會把反射路徑擋掉，要明確開例外。
  - 對手看得見的反制根本不算反制。
- **每個新機制都要教 CPU**，並且數它用了幾次、結果如何。

## 4. 美術與演出風格

詳細清單：[`skills/procedural-ink-style/reference.md`](../skills/procedural-ink-style/reference.md)。原始文件：[STYLE_STORM_DESIGN.md](STYLE_STORM_DESIGN.md)、[STYLE_STORM_RESEARCH.md](STYLE_STORM_RESEARCH.md)、[AUDIO.md](AUDIO.md)、[DUEL_MOBILE_DESIGN.md](DUEL_MOBILE_DESIGN.md)。

### 4.1 先把風格寫成數字

SOUL DUEL 的畫面是「用火影忍者 Storm 系列的技法，畫久保帶人的黑白濃淡」。這句話被拆成可以量測的規則：

- **5 階明度表**：每一階的用途都寫清楚。
- **世界的顏色**：飽和度 ≤ 0.12，色相限制在冷色帶。
- **只有 3 個點綴色**，每個都有主人：火焰的紅橙屬於山本、靈壓的黃屬於劍八、血紅留給反擊、Kikon 和 Breaker。中立畫面裡點綴色像素不超過 15%。
- **最強的對比留給角色**：世界壓在一個窄的明度帶裡，角色的明度跨度至少比世界多 60。
- **特效依材質用不同的步進率**：打擊閃光一格一張，火焰和能量兩格一張，煙塵三格一張。

形容詞（陰沉、有力）沒辦法測試，數字可以。

**怎麼做決定**：

1. **先做研究**，每條說法標等級：[V] 已驗證、[V2] 二手、[I] 推論、[U] 未驗證。[U] 永遠不拿來做決定。
2. **再請兩位立場相反的評論者**（美術、算圖工程）各自挑毛病，把每一條的裁決和兩人的衝突都記下來。
3. **讓使用者看截圖決定**：只在幾個檢查點給使用者看靜止畫面。問題都附預設答案，使用者只需要回答想改的。
4. **記錄回來**：使用者的原話、決定和造成的改動都寫進設計文件；翻案也記成翻案，免得同一件事反覆爭論。

### 4.2 程式產生的內容管線

- **角色**：每個骨架關節掛一組簡單形狀，不用蒙皮。比例用資料調（`:props`、`:girth`），所以「不要 Q 版、要寫實成人比例」只改資料就做到了。覺醒型態共用同一副骨架和受擊範圍。
- **攻擊動作**：`defstrike 名稱 (S A R ...)` 把招式的發生、持續、收招幀數寫在動作的開頭，命中姿勢自然落在第一個有效幀。動作是姿勢到姿勢：蓄力停住 → 啪一下到命名好的命中姿勢 → 過衝 → 收回站姿。`:root :f` 往前踏只是畫面效果，真正的位移是招式的 `:slide`。
- **特效**：向量的墨線形狀，跑在同一個 24 Hz 特效時鐘上；每個一次性特效都寫成 `fx-envelope` 呼叫；同一個特效最多 3 種色相。遊戲邏輯依賴的位置絕不步進化。
- **事件回報、表現層呈現**：規則只發事件，一個 feedback 系統把事件變成聲音、火花、震動。外觀只用 `rnd01`；打擊停頓和過場長度都是模擬時間。
- **過場演出**：`defcine` 跑在模擬幀上，`at` 是模擬事件，`during` 只管外觀。有一套寫下來的鏡頭文法。使用者反映「切太快」之後，改成更少、更長的鏡頭，但衝擊格保持俐落。
- **文字**：把有授權的毛筆字型在離線時烘成多邊形資料並 commit，執行期不載入任何字型檔；用測試確認沒有字幕跑出畫面。
- **音效**：`defsound` 合成；每個聲音做正規化、去直流、把循環尾巴折回開頭；啟動時一幀合成一個；混音器是純 C，不碰 Lisp 物件。衝擊前的「靜默」本身就是一個音效設計。

### 4.3 畫面要和判定對得上

這條來自使用者的試玩：「判定距離比動畫顯示的長很多」。現在它是一個 host 測試：用真實的正向運動學跑過每個型態的每一招，刀尖（或拳、腳、袖子）的位置要在判定範圍邊緣 ±0.15 m 內（`tests/duel-rules-test.lisp` 搜尋 "the volume ends"）。

兩邊對不上時，先想清楚**平衡依賴的是哪個數字**，再改另一邊：

- 千手丸的判定縮到針尖時她幾乎全輸，所以改成把針加長。
- 這次 J 拉到 1.4 m，也是讓出招動作往前踏來配合判定。

### 4.4 驗證畫面

| 檢查 | 做法 |
|---|---|
| 遊戲行為沒變 | G2 雜湊行完全相同。外觀是「純表現」，所以美術可以放心改 |
| 另一款遊戲沒變 | 它的凍結截圖逐位元相同（新畫面路徑一律是預設關閉的獨立入口） |
| 截圖可以重現 | `run.mjs --fixed-dt`，場景編成除錯整數；做成拼貼圖給使用者看 |
| 風格規則 | `tools/toon_check.py`：明度分布、彩度、點綴色比例、外框連續性 |
| 每幀 0 B | 每個新畫面路徑都有一個除錯探針，畫 N 次並記錄配置量 |

**可讀性**：

- 每個有延遲的招式都有畫出來的預兆，CPU 也讀同一個預兆，所以對雙方都公平。
- 反擊有專屬的顏色和畫面效果。
- 角色佔畫面高度的 30～48%，鏡頭和角色至少保持 3.2 m。
- 手機直式時，HUD 依玩家上下分開，文字最小 11 CSS px；用探針在四種手機尺寸量測構圖。

## 5. 開發流程與協作

詳細清單：[`skills/game-dev-workflow/reference.md`](../skills/game-dev-workflow/reference.md)。範例：[DUEL_STRINGS.md](DUEL_STRINGS.md)（功能文件的標準格式）、DEVLOG 第 78～81 節（條列式紀錄）。

### 5.1 每個需求的迴圈

1. **原話照抄**：使用者的需求（繁體中文）原封不動記下來，之後放進文件和 commit。
2. **只問會改變設計的事**：用選擇題，推薦選項放第一個；前提有誤時附來源、客氣地更正。小而清楚的需求不問。
3. **改在最小的地方**：先改角色自己的檔案；共用檔案只加通用的掛勾點。
4. **跑 gate**（第 3、4 章）。新機制在同一批或下一批教給 CPU。
5. **同一輪更新文件**：
   - 功能設計文件（英文）：引用原話，數值寫成「`*名稱*` 舊值 → 新值」，再寫測試和 gate 數字。
   - DEVLOG（中文）：新增一節，格式是 `## N. 標題（日期）`，開頭「使用者：「…」」，再條列決定、原因、改動、試過但拿掉、測試結果、還沒解決。
   - 玩家看得到的改動，要同步更新遊戲內說明頁（中文）。
   - 參考數字變了的話，所有引用它的地方都要改。
6. **重建使用者實際在玩的版本**：交付前最後一次建置一定是 `./build.sh <遊戲>`。
7. **到里程碑就 commit 並推送 main**，不用先問。
   - 主旨寫清楚改了什麼、「(the user, 日期)」、關鍵數字、文件節次。
   - 範圍限制寫在括號裡。
   - 加上署名尾行。
   - `.claude/`、暫存檔和研究筆記不 commit。
8. **只有使用者說要部署時才部署** GitHub Pages，部署後確認 Pages 狀態和網址。
9. **用中文簡短回覆**：改了什麼、關鍵數字、推送了什麼、還有什麼待定、需要使用者做什麼決定。gate 沒過、自己的疏失都直接講；沒有親眼看過的畫面要註明「需要你看」。

### 5.2 文件系統

| 文件 | 用途 | 語言 |
|---|---|---|
| README、docs/README | 入口與索引 | 中文 |
| TUTORIAL | 學習路徑 | 中文 |
| DEVLOG | 決策紀錄與理由，依日期編號 | 中文 |
| ARCHITECTURE、ENGINE_API | 模組之間的合約、坑的清單 | 英文 |
| 遊戲設計文件（照實作） | 「文件和程式碼不一致時以程式碼為準」 | 英文 |
| GAMEPLAY | 建置、除錯指令、測試腳本、gate 規則與數字 | 英文 |
| 功能／角色文件 | 一個功能一份：原話 → 決定表 → 設計 → 自我批判表 → 實作差異表 → 量測 → 之後的追加節 | 英文，給使用者看的摘要和問題用中文 |
| 遊戲內說明頁 | 玩家手冊 | 中文 |

調整用的數值全部放在程式碼的 `tuning.lisp`，docstring 寫著舊值、新值、日期、誰決定、對應哪一節文件。文件只用名字引用數值。

### 5.3 用多個 agent 平行開發

- **只平行化互相獨立的批次**：每批一個 worktree、一條 branch、**一個全新的 agent**。不要一直叫回同一個大 agent，每次叫回都要重讀整段對話。
- **brief 的骨架**：
  - 背景與使用者的決定
  - 編號步驟與確切指令
  - 每個 gate 的通過數字
  - 要改哪些文件
  - 規則
  - 回報格式
- **brief 一定要附的規則**：
  - 等待要有上限、用 PID 等。
  - 不用 `pgrep -f`／`pkill -f`：曾經有比對到自己的等待迴圈空轉 7 小時和 16 小時。
  - 不推 main、不部署、不改評分程式。
  - commit 要有署名尾行。
- **主 agent 自己重跑驗證**每份回報（測試、gate、截圖），再合併、更新文件狀態、清掉 worktree。這次就有 29 個 worktree 忘了清。
- **合約先行**：模組分工表、先寫好 stub API、動作名稱就是美術和玩法之間的合約（找不到動作就退回待機並記 log，誰都不用等誰）。
- **設計先辯論**：草案先給兩個立場相反的評論者挑毛病，再寫程式。
- **第二套實作（移植）之前先問清楚**：它是要取代原版，還是並行？之後誰負責維持一致？Babylon 版做到跟原版逐位元相同，隔天就停止開發，這是教訓。停止時要在文件頂端加橫幅、寫進狀態紀錄、更新記憶。

### 5.4 使用者的設計原則

新設計都可以拿這張清單檢查：

- **忠於原作**：每個元素標註 [漫畫]／[動畫原創]／[我們自創]，自創的名字不能看起來像原作。原作的特點寫成「對手的應對方式」，例如「千手丸正面打不贏 → 對手用距離壓她」。
- **覺醒換玩法、不換強度**：後來放寬成可以量測的 gate，見第 3.3 節。
- **猜拳式循環剋制**：防禦 > J > 抓技 > 防禦，用幾何關係和測試保證。
- **輕攻擊短而快、重攻擊長而慢**；畫面範圍就是判定範圍。
- **節奏是使用者訂的數字 gate**：刻意的削弱就保持削弱，例外只能由使用者接受。
- **攻防的平衡**：不能有無限壓制；鼓勵進攻；CPU 要能對付亂按。
- **無障礙功能做成設定裡的選項**（輔助、單手手機模式、提示），而且要有代價，而不是另開模式。

## 6. 新遊戲的啟動清單

1. **決定 repo**：同一個 repo 開新資料夾（可以直接共用引擎），或另開 repo（從範例複製 `engine/`、`vendor/`、`tools/`、`build.sh`、`compile_flags.txt`）。
2. **跟使用者確認並寫進設計文件**：類型與參考作品、風格方向、要不要確定性模擬與平衡 gate、目標平台（桌機、手機單手）、是否部署 Pages。
3. **建好骨架**：複製 `examples/hello`，寫 `MANIFEST`，然後建置、無頭截圖、`pkgcheck` 三樣都過，才開始寫玩法。
4. **確定性從第一天開始**：固定步進、vpad、兩條亂數、每場重設、雜湊行。
5. **劃好整數範圍**：除錯指令的整數範圍和頁面儲存的 key 範圍，寫成表。
6. **建立文件**：設計文件（英文、照實作）、DEVLOG（中文）、GAMEPLAY（指令與 gate）、預算表。
7. **風格寫成數字**，第一次截圖檢查點就請使用者看。
8. **建立測試**：純規則測試、第一個固定種子的參考回歸；有電腦對電腦時，及早做原生模擬 gate。
9. **之後的每個需求都走第 5.1 節的迴圈。**

## 7. 附錄：坑與解法速查

| 坑 | 解法 | 出處 |
|---|---|---|
| 從 Lisp 呼叫 GC 造成記憶體損壞 | GC 只在幀之間跑 | DEVLOG §3、ARCHITECTURE "The GC rule" |

| 引擎 Lisp 和 C 在建置途中被別人改掉 | 引擎工作放到獨立 worktree | DEVLOG §14.1 |
| 自我比對的 `pgrep -f` 等待迴圈永遠不結束 | 用 PID 等、迴圈設上限 | 記憶 feedback-no-self-matching-pgrep |
| 原生模擬過了，手機卻是舊版 | 最後一定 `./build.sh <遊戲>` | 記憶 feedback-rebuild-dist |
| 頁面儲存的 key 範圍撞號 | 一開始就劃好範圍並列表 | DEVLOG §67 |
| 網頁版 service worker 把新 html 配上舊 wasm | 單一版本快取、全部 cache-first | DEVLOG §15 |
| `pointerdown` 不算使用者手勢 | 全螢幕、音訊恢復掛在 `pointerup`／`touchend` | DEVLOG §15 |
| 判定比動畫長 | 用正向運動學的距離測試；改平衡不依賴的那一邊 | DEVLOG §32、DUEL_STRINGS §13、§20 |
| 多擲一次骰子讓 A/B 結果全部重洗 | 機率 0 不擲骰、計數不擲骰、三條種子流 | DEVLOG §25、§27 |
| CPU 的反應規則永遠不觸發 | 用自己立刻感覺得到的狀態決定 | DUEL_STRINGS §9、DEVLOG §74 |
